# Infomil Mauritius — Point quotidien

Application Next.js App Router, React, TypeScript et **Tailwind CSS v4**, migrée depuis le site HTML/JavaScript. L’interface et les comportements restent en français. L’ouverture directe de fichiers locaux (`file://`) n’est plus prise en charge : utilisez le serveur Next.js.

## Un dépôt, deux applications Vercel

**Ce monorepo est la source active des deux sites.** Le maître reste à la racine pour préserver son projet Vercel existant ; le portail participants et les packages partagés appartiennent au même dépôt Git.

| Emplacement | Responsabilité |
| --- | --- |
| Racine `.` et [src](src) | Application Scrum Master existante, API serveur et accès Neon. |
| [apps/participants](apps/participants) | Application participants : notes, statistiques et bilan ; déploiement Vercel distinct. |
| [packages/scrum-shared](packages/scrum-shared) | Package workspace `@infomil/scrum-shared`, utilisé par les deux applications. |
| [src/db/schema.ts](src/db/schema.ts) et [drizzle](drizzle) | Schéma serveur et migrations canoniques, uniquement à la racine. |

L’ancien dossier frère **scrumParticipants** reste intact comme sauvegarde historique, **pas comme source active**. Aucun second dépôt Git ni dépôt imbriqué n’est nécessaire. Le [guide du portail](apps/participants/README.md) complète les instructions ci-dessous.

## Installation et commandes

Node.js **>= 20.9** et npm sont nécessaires. Depuis la racine du projet :

| Commande | Usage |
| --- | --- |
| `npm install` | Installer à la racine les dépendances des deux applications et lier les workspaces partagés. |
| `npm run dev` | Préparer les ressources puis lancer le développement sur http://localhost:3000. |
| `npm run build` | Préparer les ressources puis créer le build de production. |
| `npm run start` | Servir un build de production existant. |
| `npm run lint` | Vérifier les règles ESLint. |
| `npm run typecheck` | Vérifier TypeScript sans émission. |
| `npm run test` | Lancer le runner Node sur les tests TypeScript ; nécessite une version de Node prenant en charge `--experimental-strip-types` (Node >= 22.6). |
| `npm run dev:participants` | Lancer le portail en développement sur http://localhost:3002. |
| `npm run build:participants` | Créer uniquement le build de production du portail. |
| `npm run start:participants` | Servir le build existant du portail sur http://localhost:3002. |
| `npm run lint:participants` | Vérifier ESLint pour le portail. |
| `npm run typecheck:participants` | Vérifier TypeScript pour le portail. |
| `npm run test:participants` | Lancer les tests du portail. |
| `npm run assets` | Republier les ressources navigateur dans [public](public). |
| `npm run db:generate` | Générer une migration Drizzle après modification du schéma. |
| `npm run db:check` | Vérifier la cohérence des migrations Drizzle. |
| `npm run db:verify` | Vérifier la connexion Neon, les tables et le journal Drizzle sans afficher de données privées. |
| `npm run db:migrate` | Appliquer les migrations versionnées à Neon avant le déploiement. |

Toutes ces commandes se lancent depuis la racine. Les scripts sans suffixe ciblent le maître ; les variantes `:participants` délèguent au workspace du portail. **Une seule installation npm à la racine** génère/met à jour l’unique [package-lock.json](package-lock.json), versionné dans Git pour tout le monorepo. Ne pas créer de lockfile ni d’installation autonome dans le portail ou le package partagé. Les commandes de base de données restent propres au maître.

Les [tests de domaine](tests/domain.test.ts) couvrent la normalisation, les transformations de données, les prérequis de session, le mélange, les échéances et les chemins du catalogue ; ils ne prouvent pas un import automatique d’anciennes données navigateur. Node 22.6+ est conseillé pour utiliser toutes les commandes, même si le minimum de l’application est 20.9.

### Page sans styles ou bloquée sur le chargement

Pour modifier l’interface, privilégiez `npm run dev` : les changements sont actualisés automatiquement. Un serveur lancé avec `npm run start` utilise le build chargé à son démarrage. **Arrêtez tous les serveurs de production de ce projet avant `npm run build`, puis redémarrez-les une fois le build terminé.** Sinon, les anciennes pages peuvent demander des fichiers CSS/JavaScript remplacés et recevoir des erreurs HTTP 500.

Après le redémarrage, rechargez la page (Ctrl+F5 si nécessaire). Les données métier durables sont dans Neon et partagées entre les appareils autorisés du même déploiement. Ni cookies, ni `localStorage`, ni IndexedDB ne conservent les équipes. La connexion Jira utilise toutefois des cookies HttpOnly opaques pour sa session et son état OAuth. Le minuteur utilise un point de reprise temporaire dans `sessionStorage`, limité au même onglet et restauré après une lecture Neon réussie ; ce n’est pas un mode hors ligne.

## Jira Cloud et équipes sprint

La création distingue **Ordinaire** (membres saisis manuellement, sans connexion Jira) et **Sprint Jira** (site autorisé, tableau Scrum visible et sprint actif). La connexion Jira apparaît dans le panneau de création après sélection de **Sprint Jira**, et non dans l’en-tête de l’annuaire. Les équipes existantes restent ordinaires. Une équipe sprint exige une connexion Jira et le droit de voir son tableau, vérifié côté serveur à chaque requête métier. Sans accès, l’annuaire affiche uniquement son nom et son type, avec la mention **Connexion Jira requise** ; **Ouvrir** ou **Gérer** propose alors la connexion sans sélectionner ni charger cette équipe. Le nombre de membres, la catégorie, les favoris et le sprint restent masqués. Ce contrôle ne signifie pas que l’utilisateur connecté possède lui-même un ticket dans le sprint.

À la création, le **premier site Jira accessible renvoyé par l’API** est sélectionné automatiquement, sans menu de site. Seuls le tableau Scrum et le sprint actif restent à choisir. Si aucun site n’est accessible, la création reste bloquée avec un message explicite ; un échec de lecture propose **Réessayer**. La synchronisation d’une équipe existante conserve son site et son tableau enregistrés.

### Configuration serveur

L’opérateur de l’intégration crée et gère **une seule application OAuth 2.0 (3LO) distribuable** dans la [console Atlassian](https://developer.atlassian.com/console/myapps/), conformément au [guide 3LO](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/). Activer **Distribution → Enable sharing** pour permettre à d’autres comptes de se connecter. Ne pas demander à chaque participant de créer sa propre application ni de fournir un jeton API.

Ajouter les API **Jira Software**, **Jira Platform** et **User Identity**, puis les autorisations suivantes, également demandées par le code :

```text
read:me
offline_access
read:board-scope:jira-software
read:project:jira
read:sprint:jira-software
read:issue-details:jira
read:jql:jira
```

Configurer sur le **maître uniquement**, sans préfixe `NEXT_PUBLIC_` et sans secrets dans Git :

| Variable | Valeur |
| --- | --- |
| `JIRA_CLIENT_ID` | Client ID de l’application partagée. |
| `JIRA_CLIENT_SECRET` | Secret client conservé côté serveur. |
| `JIRA_CALLBACK_URL` | URL exacte du maître terminant par `/api/jira/callback`, sans paramètres ni fragment. Elle doit correspondre à **Authorization → OAuth 2.0 (3LO) → Callback URL**. HTTPS en production ; par exemple `http://localhost:3001/api/jira/callback` en local. |
| `JIRA_ENCRYPTION_KEY` | Clé cryptographique aléatoire de **32 octets, encodée en 64 caractères hexadécimaux**. La conserver identique sur toutes les instances ; son remplacement invalide les anciennes connexions Jira. |

**Avant de démarrer ou déployer cette version, appliquer [0010_jira_sprint_teams.sql](drizzle/0010_jira_sprint_teams.sql) avec `npm run db:migrate`, puis `npm run db:verify`.** Même l’annuaire ordinaire consulte la nouvelle relation pour filtrer les équipes sprint. La migration ajoute uniquement les relations de sprint, états OAuth et sessions Jira ; elle ne convertit ni ne supprime d’équipe existante. Sur la base Neon configurée de ce poste, elle a été appliquée avec autorisation via le migrateur HTTP Drizzle existant après l’échec DNS/WebSocket du CLI ; la vérification confirme 21 tables, 94 colonnes, 11 migrations et aucun défaut d’intégrité. Les autres environnements doivent appliquer leur propre journal. Le serveur doit pouvoir joindre `auth.atlassian.com` et `api.atlassian.com` en HTTPS ; l’adaptateur proxy Neon ne couvre pas Jira.

### Participants et tickets

Le roster importé contient les **responsables des tickets du sprint visibles par le compte effectuant l’import**, dédoublonnés par `accountId`. Les tickets non attribués sont exclus ; ce n’est pas une liste Jira Teams, de projet ou de membres déclarés du sprint. Un import vide, incomplet, dépassant 100 personnes ou contenant des noms incompatibles avec la limite de 60 caractères est refusé, sans import partiel. Les autorisations Jira peuvent donc limiter la liste importée.

Les identités et noms d’une équipe sprint ne sont pas modifiables manuellement, y compris par l’API. **Gérer l’équipe → Sprint Jira → Synchroniser les participants** remplace explicitement le roster depuis un sprint actif du même tableau, après confirmation. Les présences des personnes conservées restent inchangées, les nouvelles personnes sont présentes, les humeurs sont effacées et les bilans archivés restent conservés. Les révisions concurrentes ou une erreur d’import annulent l’opération. Aucun changement automatique de sprint ou de roster n’intervient. La synchronisation est bloquée lorsqu’un tour est préparé dans l’onglet ; ce verrou local ne détecte pas un minuteur actif sur un autre appareil.

Le minuteur charge les **Tickets Jira** du tableau de l’équipe uniquement pour le groupe de statuts sélectionné : **À faire**, **En cours** (par défaut) ou **Terminés**. Le filtre `statusCategory` est envoyé à Jira sur chaque page ; aucun téléchargement initial de tous les statuts ni préchargement des groupes non choisis n’a lieu. Les libellés de statut propres à Jira restent affichés dans les tickets. **Intervenant** filtre ensuite localement les tickets du responsable courant ; **Tout le tableau** affiche aussi ceux des autres responsables et les tickets non attribués, toujours dans le groupe sélectionné, avec recherche locale et pagination. Chaque nouveau passage conserve le groupe de statuts et revient au filtre de l’intervenant sans nouvelle requête. La liste provient du tableau Jira (tickets visibles dont le statut appartient à ses colonnes), pas seulement du sprint importé, ni de tous les tickets du projet. Les couleurs de statut suivent la catégorie réellement fournie par Jira, sans déduire une catégorie depuis son libellé. La lecture suit les droits Jira du compte connecté et ne modifie pas le décompte. Aucun ticket n’est créé ou modifié dans Jira ; leurs contenus ne sont ni archivés dans Neon ni envoyés à la télécommande ou au direct.

Les lectures identiques en cours sont regroupées. Le panneau conserve son instantané pendant le point, même lors d’un changement d’intervenant ou du passage aux questions ; **Actualiser** recharge uniquement le groupe de statuts sélectionné en contournant les caches navigateur et serveur. Revenir à un autre groupe réutilise son cache s’il est encore valide. Le cache navigateur distingue équipe et URL (statut inclus) et expire après **60 secondes** (15 secondes pour les autres ressources Jira). Le cache serveur distingue jeton d’accès, site, tableau et groupe de statuts ; les lectures de sprint conservent une clé séparée. Il expire après 60 secondes. **Chaque requête serveur revérifie l’accès au tableau avant de consulter ce cache.** Les deux caches sont limités à 64 entrées, sans persistance navigateur ni cache distribué entre instances ; leurs fenêtres d’expiration peuvent se cumuler. Les imports relisent Jira, et une synchronisation ou déconnexion vide le cache navigateur. Les erreurs ne sont pas mises en cache ; une perte d’autorisation efface les entrées navigateur.

Les métadonnées des baromètres partagent aussi leurs lectures en cours : une navigation annulée ne coupe pas la requête utile à une autre vue. Le catalogue reste en mémoire une minute et les présentations résolues cinq minutes (20 présentations au maximum). Les diapositives du baromètre démarrent en parallèle, sans attendre la première image ; chaque image conserve ses propres reprises et son état de chargement.

Les jetons d’accès et de renouvellement sont chiffrés AES-256-GCM dans Neon, jamais retournés au navigateur. La session opaque HttpOnly/SameSite=Lax expire après **8 heures**, sans prolongation automatique de cette limite ; les jetons Jira sont renouvelés et remplacés pendant cette période. L’état OAuth est lié au navigateur, valable 10 minutes et utilisable une seule fois. **Déconnecter Jira** supprime la session de ce navigateur, sans déconnecter le compte Atlassian ni révoquer son consentement ; la révocation se fait dans le compte Atlassian.

Le **portail participants sans connexion personnelle est réservé aux équipes ordinaires** : émission et usage de liens refusés pour les équipes sprint. Les données de ces équipes restent accessibles depuis le maître après connexion Jira. Le direct d’une équipe sprint exige également cette connexion ; le lien explicite de télécommande demeure une capacité de contrôle du minuteur, sans accès aux tickets.

Les [tests Jira](tests/jira.test.ts) couvrent OAuth simulé, chiffrement, renouvellement, visibilité, imports, révisions et rollback dans PGlite. `python tests/jira_smoke.py` vérifie huit parcours à quatre tailles d’écran dans les deux modes de mouvement, deux parcours de connexion contextuelle mobile et bureau (création, ouverture, gestion et annulation), ainsi que les cas sans site et de reprise après erreur, avec API entièrement simulées. La sélection du premier site parmi plusieurs est vérifiée sans menu de site ; `python tests/team_directory_smoke.py` couvre les équipes ordinaires sans configuration Jira. Ces contrôles ne prouvent ni une connexion Atlassian réelle ni une migration Neon effective.

## Parcours et comportement

### Deux projets Vercel : maître et participants

L’application racine reste le site **Scrum Master** : équipes, membres, présences, baromètres, minuteur avec pense-bête pendant la parole et résumé de fin de tour/jour. Le second site est l’application [apps/participants](apps/participants) du **même dépôt** : vues complètes **Notes / Statistiques / Bilan**, avec notes modifiables et statistiques/bilan en lecture seule. Les anciennes routes autonomes `/daily-notes` et `/statistics` du maître sont retirées (HTTP 404), sans lien dans sa navigation. Le portail ne dépend d’aucun pilote ou schéma de base de données partagé, ne reçoit pas `DATABASE_URL` et n’exécute aucune migration ; ses requêtes serveur passent par l’API dédiée du maître.

Configuration Vercel faisant autorité :

1. **Maître existant : ne rien déplacer et conserver Root Directory `.`**, framework **Next.js**, build `npm run build` à la racine.
2. Créer un **nouveau projet Vercel en important le même dépôt Git**, framework **Next.js**, **Root Directory `apps/participants`**. Activer **Include source files outside of the Root Directory in the Build Step** pour inclure les packages partagés.
3. Conserver l’installation automatique native **npm workspaces**, détectée depuis le lockfile racine versionné ; laisser **Install Command** sans surcharge. Ne pas contourner cette détection avec une commande personnalisée, `--prefix`, une copie de package ou un second lockfile.
4. Pour le portail, le build est **`npm run build` exécuté depuis la Root Directory de l’application**, pas le build du maître à la racine. Les deux projets conservent la sortie Next.js standard. Vérifier dans les journaux Vercel la détection du workspace et du lockfile racine.
5. Conserver les variables serveur ci-dessous, séparément pour chaque projet et environnement utilisé, puis redéployer. Le portail n’a besoin ni d’accès direct à Neon ni du corpus d’assets du maître.

Configurer sur le maître `PARTICIPANT_PORTAL_URL` (origine HTTPS du second site, sans chemin) et `PARTICIPANT_PORTAL_SECRET` (secret aléatoire partagé d’au moins 32 caractères, sans espace). Sur le portail, configurer `SCRUM_MASTER_URL` (origine HTTPS de ce site) et le même `PARTICIPANT_PORTAL_SECRET`. Aucun préfixe `NEXT_PUBLIC_` et aucun secret dans Git. Pour tester localement, les origines HTTP localhost sont acceptées. Déployer les deux projets après configuration ; aucune migration supplémentaire n’est nécessaire pour ce raccordement (les tables de notes doivent déjà exister).

Dans **Gérer l’équipe → Lien participants**, copier le lien signé de l’équipe. Le portail ne propose pas d’annuaire ni de changement d’équipe. Le lien HMAC couvre un identifiant d’équipe ; modifier cet identifiant invalide la signature. L’API `/api/participant-portal` exige à la fois le secret serveur et le lien signé, ne fournit que le roster simplifié, les notes et les bilans, et n’accepte en écriture que les notes validées avec jour mauricien et révision concurrente. Les routes de gestion existantes ne sont pas exposées par le proxy du portail. La rotation du secret invalide tous les liens ; aucune révocation individuelle ni expiration automatique n’est promise.

Les notes sont des chaînes **Markdown** dans le champ `hint`, jamais du HTML ni du JSON d’éditeur. Le serveur ne retire que les espaces extérieurs ; les marqueurs comptent dans la limite de 600 points de code Unicode. Le pense-bête du minuteur et sa fenêtre de lecture affichent gras, italique, texte barré, listes, paragraphes et retours LF avec `react-markdown` et `remark-gfm`. Les notes historiques en texte simple restent lisibles. Aucun HTML brut, lien cliquable, image ou ressource incorporée n’est autorisé dans ce rendu. Le maître n’édite pas les notes ; la sauvegarde explicite du portail conserve le Markdown, sans nouvelle tentative automatique d’écriture. Aucun changement de schéma n’est nécessaire.

Lorsque tous les passages sont terminés, l’enregistrement réussi du bilan supprime toutes les notes de cette équipe, y compris celles des absents, dans la même transaction. L’expiration d’un minuteur individuel ne les supprime pas. En cas d’échec, bilan et suppression sont annulés ensemble ; les autres équipes restent intactes. Une nouvelle tentative du même bilan ou un bilan concurrent rejeté ne supprime pas les notes créées après la fin du tour.

**Pour une équipe ordinaire, sans connexion personnelle**, toute personne possédant le lien peut consulter ses données et modifier la note de n’importe lequel de ses membres. Ne pas publier le lien ni y placer de données sensibles. Ce partage ne sécurise pas les autres routes ordinaires du maître ; les équipes sprint exigent séparément Jira et n’acceptent pas ces liens. Aucun lien réel ni secret n’a été généré ou publié par l’implémentation. Le [guide du portail](apps/participants/README.md) détaille son déploiement distinct depuis le même dépôt et les en-têtes de confidentialité.

- **`/teams`** : écran de démarrage avec recherche des équipes, ouverture, accès à la gestion et création. La racine `/` redirige vers cette route.
- L’annuaire propose une liste responsive sur toute la largeur et le bouton **Ajouter une nouvelle équipe** au-dessus de la liste. Il ouvre une fenêtre avec le type d’équipe, son nom et les choix Jira éventuels ; **Annuler** ou Échap ferme la fenêtre sans création et rend le focus au bouton. Les catégories d’équipe ne sont plus proposées, affichées ni utilisées dans la recherche ; les nouvelles équipes sont créées sans catégorie et les anciennes valeurs en base restent inchangées. La recherche porte sur les noms et se combine avec les vues Toutes / Mon équipe / Favorites. **Mon équipe** désigne uniquement l’équipe actuellement sélectionnée, pas une appartenance personnelle. L’étoile ajoute ou retire un favori. Les favoris sont **partagés entre tous les visiteurs**, enregistrés dans Neon sans stockage navigateur ; ces changements ne sélectionnent pas une autre équipe et ne réinitialisent ni ses présences ni son minuteur. Appliquer la migration [0006](drizzle/0006_pretty_shiver_man.sql) avec `npm run db:migrate` **avant de déployer** cette version. La migration conserve les équipes, membres et bilans, et initialise les favoris à faux. Ce retrait des catégories de l’interface ne nécessite pas de nouvelle migration.
- L’écran Gérer l’équipe propose **Supprimer l’équipe** avec recopie du nom exact. La suppression est définitive et partagée : participants (y compris identités archivées), présences, humeurs, baromètres propres à l’équipe, bilans, passages, retours et questions personnalisées sont supprimés dans une transaction. Les autres équipes, espaces techniques et le catalogue global sont conservés. Les anciennes références de sélection sont libérées. Les dépendances restrictives sont supprimées avant la ligne équipe, puis les clés étrangères terminent la cascade ; toute erreur annule l’ensemble. Aucun changement de schéma n’est nécessaire. Après suppression de la dernière équipe, la liste reste vide, même après rechargement, jusqu’à une création explicite. Les sauvegardes en attente bloquent la suppression ; une réponse non confirmée bloque les modifications jusqu’à une nouvelle lecture Neon.
- **`/manage-team`** : ajouter, rechercher, renommer et retirer les membres, individuellement ou par sélection avec confirmation. Une nouvelle équipe ouvre cet écran.
- **`/participants`** : confirmer uniquement les présences et absences du jour, puis continuer vers les humeurs. Le lien « Gérer l’équipe » ouvre la gestion des membres.
- **`/mood`** : consulter les baromètres locaux (fonds et GIF), choisir une humeur **1–4** pour chaque personne présente. Les GIF jouent automatiquement en boucle au chargement et à chaque changement de diapositive ou de baromètre, y compris si la réduction des mouvements est activée (lecture explicite demandée). **Stop / Reprendre** fige ou reprend les animations de la diapositive actuelle ; **Précédente / Suivante** changent manuellement de diapositive. Aucun changement automatique de diapositive. Les autres animations de l’interface respectent la réduction des mouvements. Au moins une personne présente et toutes ses humeurs sont nécessaires pour continuer.
- **`/timer`** : ordre mélangé contenant uniquement les présents, minuteur par personne, pause, réinitialisation, ajout de 30 secondes, préalerte et fin sonore facultative. Le passage suivant reste manuel.

Uniquement depuis Participants, **Continuer vers les humeurs** ouvre une fenêtre de préparation : toutes les personnes présentes, y compris celles en attente, apparaissent en cartes et se mélangent pendant **trois secondes** avec de longs déplacements fluides, sans partition réservée aux reports ; les absents sont exclus. Après la révélation et une pause de lecture, les cartes s’effacent doucement et la page des humeurs apparaît. La fermeture automatique ou **Aller aux humeurs** conserve cet ordre transitoire en mémoire React pendant les votes, puis **Continuer vers le minuteur** le reprend sans nouvelle fenêtre ni nouveau mélange et sans démarrer le décompte. Aucune session n’est créée avant cette dernière action. **Annuler** ou Échap reste sur Participants sans appliquer le nouvel ordre. Il n’existe plus de commande de mélange sur le minuteur ni de tirage ultérieur : pour préparer un autre ordre, revenir aux participants. Un rechargement efface l’ordre de préparation avant la création de la session ; ensuite, l’ordre du tour fait partie du point de reprise temporaire du minuteur dans cet onglet. En mouvement réduit, l’ordre final apparaît sans mélange animé. Les grandes équipes défilent dans la fenêtre, sans déplacer ses commandes. Le test [lineup_reveal_smoke](tests/lineup_reveal_smoke.py) couvre les déplacements réels, la durée du mélange, cinq formats d’écran dans les deux modes de mouvement, la conservation de l’ordre à travers les votes jusqu’au minuteur, les reports/absences, l’annulation, Échap, le passage immédiat et la réouverture depuis Participants avec des API simulées.
- **`/help`** : guide illustré en français (lien « Guide » dans le bandeau), accessible même pendant une panne Neon ou après le point du jour. Les quatre illustrations originales sont conservées dans `docs/guide` et publiées par `npm run assets`, jamais modifiées directement dans `public`.

Le bouton **Détail du score** de chaque participant ouvre son temps actif, le pourcentage du budget et le calcul des points. Le bilan transitoire peut détailler les relances connues. Les bilans enregistrés et les points récents affichent le score conservé, le calcul selon le barème actuel et leur écart : les archives ne stockent ni le nombre de relances ni la version du barème, donc aucune cause n’est inventée pour cet écart et aucun ancien total n’est réécrit.

Le **Bilan du jour** présente un tableau de bord compact sans défilement : bandeau de quatre indicateurs, classement paginé selon la hauteur disponible et deux colonnes sur grand écran. Sur mobile et tablette étroite, les boutons « Points & détails » et « Mood meters » alternent les sections sans les empiler. Les choix d’humeur sont filtrables par repère dans l’ordre 1–4 / 2–3 et paginés ; un sélecteur permet de consulter plusieurs baromètres. Sur les écrans courts, « Voir image » ouvre la diapositive dans une fenêtre. Les graphiques ne recalculent pas les scores archivés ; les durées excluent les pauses. La réinitialisation conserve sa confirmation et sa portée partagée pour toute l’équipe.

Le bilan développé sépare deux colonnes : **points et explications** à gauche (indicateurs, classement, zones temporelles) et **baromètres et choix** à droite. Les choix sont groupés par diapositive exacte puis par repère 1–4, avec noms et couleurs distinctes non évaluatives. L’aperçu utilise uniquement la diapositive d’un choix individuel encore inchangé, daté avant la fin du tour et cohérent avec le titre et l’humeur archivés. Sans cette preuve, le titre et les groupes restent visibles avec un message d’image indisponible ; aucun rapprochement approximatif par titre n’est tenté. Les GIF restent en pause jusqu’à une action explicite et désactivés en réduction des mouvements. Entrées et barres de score ont des animations discrètes, sans mouvement sous réduction des animations.

**Démarrer** ouvre le mode de parole : bandeau précédent / personne active centrée / personne suivante, minuteur agrandi et réglages verrouillés (y compris en pause). **Modifier** suspend le décompte et ouvre une fenêtre de réglages ; fermer cette fenêtre garde le minuteur en pause, sans quitter le mode de parole. **Suivant** termine le passage actuel et démarre immédiatement le minuteur de la prochaine personne ; à zéro, le passage reste manuel, sans changement automatique. Le dernier passage termine le tour et arrête le minuteur. Le rechargement reprend le contexte de cet onglet après vérification de l’équipe dans Neon.

**Précédent** revient à la personne précédente dans l’ordre du tour, en ignorant les passages reportés et sans boucler depuis la première personne. Son passage redevient disponible avec un décompte complet **en pause** ; les temps actifs, budgets, relances et pénalités des deux personnes sont conservés. Le passage quitté n’est pas marqué terminé. Le prochain démarrage du passage rouvert compte comme une relance selon le barème existant. Le bouton est désactivé au premier passage et ne rouvre pas un bilan terminé.

Après le dernier passage, un classement et le bilan du tour apparaissent. Le score de gestion du temps se consulte **uniquement en fin de tour et dans l’historique, pas en direct sur le minuteur**. Le barème utilise une **référence fixe en secondes de temps actif cumulé, indépendante du budget configuré, même si celui-ci diffère de 120 s**. Jusqu’à **5 s incluses : 0 point** (grâce). Après 5 s et jusqu’à 105 s : **max(125, (temps actif − 5) × 10)**, soit **1 000 points à 105 s**. De 105 à 110 s, retirer 5 points par seconde (975 à 110 s) ; de 110 à 115 s, retirer 10 points par seconde (925 à 115 s) ; de 115 à 120 s, retirer 15 points par seconde (**850 à 120 s**). Après 120 s, retirer **50 points par tranche de 10 secondes entièrement écoulée**, avec un **plancher de 125 points atteint à 270 s** : le score reste à 850 de 120 s à moins de 130 s, puis à 800 de 130 s à moins de 140 s. Exemples hors pénalités de relance, quel que soit le budget : **30 s = 250 pts ; 60 s = 550 pts ; 105 s = 1 000 pts ; 110 s = 975 pts ; 115 s = 925 pts ; 120 s = 850 pts ; 130 s = 800 pts ; 140 s = 750 pts ; 270 s = 125 pts**.

À zéro, le chronomètre continue en dépassement positif jusqu’à Pause ou Suivant, sans changer automatiquement de personne ; l’alerte sonore et la notification ne se déclenchent qu’une fois. Une relance après réinitialisation retire **100 points, maximum 200**, sans descendre sous **125 après 5 secondes** ; la grâce jusqu’à 5 s incluses reste à **0**, même avec des relances. Pause/reprise, y compris en dépassement, ne pénalise pas et exclut le temps de pause. Le score final est arrondi au point entier. Le budget initial et le temps actif cumulé sont conservés lors des réglages et relances, sans déplacer les seuils fixes du score. Un passage terminé de moins d’une seconde reste non mesuré. Ce jeu n’évalue ni la qualité de la contribution, ni la productivité, ni les humeurs ; les égalités partagent le rang. Le bilan présente le temps actif, la moyenne, les passages dans le temps et les dépassements, ainsi que la répartition des repères d’humeur. Chaque choix d’humeur conserve son baromètre et sa diapositive : les images et les personnes associées figurent dans le bilan, avec lecture GIF facultative. Les mêmes nombres sur différents baromètres n’ont pas forcément le même sens. Le bilan détaillé courant reste en mémoire ; à la fin du tour, une copie compacte des noms, catégories, titres des baromètres, durées et scores rejoint l’historique des 5 derniers jours, sans images ni progression active. Les scores déjà archivés restent inchangés, sans recalcul rétroactif.

Chaque page indique son étape et l’action suivante. Les présences et les états prêts/terminés sont verts ; les absences et le temps écoulé sont rouges ; les informations incomplètes et les avertissements sont orange. Le minuteur passe à l’orange au seuil configuré, puis au rouge dans les dernières secondes (10 secondes maximum, ou la moitié du seuil). Les halos pulsent doucement uniquement pendant le décompte, jamais en pause ni avec la réduction des mouvements. Désactiver la préalerte désactive ces étapes avant zéro. À zéro, une notification urgente et un message persistant demandent de conclure et de passer la parole ; aucun passage automatique n’a lieu.

Ce sont de vraies routes Next.js, pas des vues à fragments d’URL. Les gardes attendent une lecture Neon réussie puis empêchent de sauter les prérequis ; si Neon est inaccessible, le démarrage reste bloqué avec une erreur explicite et des tentatives automatiques. Modifier une présence ou une humeur invalide la session. Quitter la route du minuteur nettoie ses intervalles, mais conserve son point de reprise dans cet onglet : une échéance active continue de compter le temps écoulé au retour. La personne active reste en place après le démarrage, y compris en pause ; aucun mélange n’est proposé sur le minuteur. Raccourcis : **Espace** démarrer/pause, **N** suivant, **R** réinitialiser, sans intercepter les contrôles natifs ou les dialogues.

Préserver les contrôles accessibles, le focus visible, les notifications en français, les listes paginées, les panneaux adaptés aux petits écrans et la réduction des mouvements (animations et GIF).

## Architecture

### Package partagé et frontière serveur

[packages/scrum-shared](packages/scrum-shared) centralise les **schémas de validation à l’exécution, contrats, types, helpers de dates et statistiques, et UI réutilisable**. Les exports `@infomil/scrum-shared/contracts`, `/types`, `/daily-hints` et `/statistics` restent distincts de l’export client **`@infomil/scrum-shared/ui`** : importer l’UI n’entraîne aucune dépendance serveur ou base de données. Les deux applications consomment ces sources TypeScript/TSX via les workspaces ; Next.js transpile le package et Tailwind analyse ses sources UI.

Les schémas de validation partagés ne sont **pas** le schéma de stockage : [src/db/schema.ts](src/db/schema.ts), [drizzle](drizzle), les adaptateurs Neon, les secrets et les services serveur du maître restent canoniques à la racine uniquement. Le proxy et ses secrets restent côté serveur du portail ; aucun de ces modules n’entre dans les exports UI partagés.

### Notes quotidiennes de préparation

La préparation, la recherche et l’édition des notes (600 caractères maximum, membres absents inclus) appartiennent exclusivement à l’onglet **Notes du portail participants**, accessible par **Gérer l’équipe → Lien participants**. Il n’existe plus de page autonome de notes sur le maître. Les notes restent partagées avec l’équipe, sans authentification personnelle ; elles ne sont pas privées. Les services, contrats, stockage et API du maître restent en place pour le portail et le minuteur.

Les notes suivent le jour civil **à Maurice (`Indian/Mauritius`, UTC+4)**. Les anciennes notes disparaissent de l’interface au changement de jour ; leur suppression physique en base s’effectue à la prochaine lecture ou écriture du service, pour toutes les équipes. Il s’agit d’un nettoyage à la demande, **pas d’une tâche planifiée à minuit**. La clé équipe–participant garantit une seule note par personne, et une révision optimiste refuse les modifications concurrentes plutôt que d’écraser une note. Le brouillon reste dans la fenêtre en cas de conflit et doit être confirmé après lecture de la version enregistrée ; aucune sauvegarde n’est rejouée automatiquement.

Le minuteur affiche un aperçu de la note de la **personne active uniquement** et le bouton **Pense-bête** ouvre son texte complet. Le changement de personne recharge les notes du jour. Lire ou fermer ce dialogue ne suspend ni ne réinitialise le décompte. Les notes ne sont ni incluses dans les scores ni archivées avec les bilans, et aucun stockage navigateur n’est ajouté.

**Avant de déployer cette fonctionnalité, appliquer la migration [0005](drizzle/0005_tired_black_bird.sql)** avec le journal Drizzle existant, puis vérifier la base avec `npm run db:verify`. Elle ajoute la table relationnelle `participant_daily_hints`, avec suppression en cascade des identités/équipes supprimées ; aucune table n’est créée par les requêtes de l’application. Les [tests de notes](tests/daily-hints.test.ts) couvrent validation, migrations, isolation, révisions et expiration dans PGlite. Le [smoke du minuteur](tests/timer_turn_smoke.py) conserve la lecture du pense-bête, le rendu texte, le changement de personne et l’absence de pause lors de la lecture. Le [smoke du portail](apps/participants/tests/portal_smoke.py) couvre l’édition, les conflits et les erreurs avec API simulées. Les anciennes suites des pages autonomes Notes et Statistiques du maître ont été supprimées ; les vues complètes se valident désormais dans le portail.

### Tableaux de bord adaptés à l’écran

Le résumé du jour du maître conserve une composition bornée par la hauteur disponible, notamment sur les écrans **16:9 (1024×576, 1366×768 et 1920×1080)** : hiérarchie compacte, indicateurs, surfaces légères et listes paginées. Ses deux colonnes points/humeurs sur grand écran et ses onglets sur mobile restent disponibles via `DailyRound` / `DailyDashboard` ; le bilan transitoire `SessionResults` reste également conservé. Les vues complètes de statistiques et de bilan appartiennent au portail participants, avec recherche et pagination. Le retrait des pages autonomes maître ne change ni le barème, ni les données enregistrées, ni la rétention, ni les API de notes/historique/partage.

### Chargement et consommation de ressources

À chaque ouverture ou rechargement du site, une introduction « Mood Meter » couvre la première page pendant cinq secondes au maximum. Les données et la route se chargent en parallèle derrière cet écran ; « Passer l’intro » ou Échap le ferme immédiatement. Les cartes d’humeur, halos et la progression sont animés uniquement sans préférence de mouvement réduit. Aucun stockage n’est utilisé et la navigation interne ne rejoue pas l’introduction. La vue spectateur en est exemptée. L’invitation au plein écran sur ordinateur apparaît ensuite. Cette introduction n’indique pas que les données sont prêtes : les squelettes et erreurs habituels restent visibles après sa fermeture si nécessaire.

Le baromètre distant charge ses images **dans l’ordre** : première diapositive prioritaire, puis deuxième après la réussite de la première (ou l’épuisement de ses tentatives), et ainsi de suite. Les emplacements suivants gardent un squelette stable sans lancer d’export Google concurrent. Les lectures de catalogue/présentation et les images échouées ont au maximum **trois nouvelles tentatives**, après **1 s, 1 s et 2 s** (Fibonacci), soit quatre essais au total. Les lectures HTTP ne réessaient que les erreurs réseau et les statuts temporaires 408/429/500/502/503/504, jamais les refus 403/404 ; aucune écriture quotidienne n’est rejouée automatiquement. Changer de baromètre ou quitter la page annule les temporisations. Après épuisement, l’erreur ou le baromètre de secours reste explicite. Le chargement à froid dépend toujours du réseau et de Google ; les caches existants accélèrent les réouvertures.

Les lectures identiques partagent désormais un **cache serveur en mémoire** : 5 secondes pour la liste des équipes, leur état, les bilans, le baromètre quotidien, les questions et les retours ; 60 secondes pour le catalogue public et les présentations. Les requêtes simultanées de même clé partagent une seule lecture Neon. Chaque modification métier invalide le cache d’équipe avant et après l’écriture, y compris en cas d’échec ambigu ; les écritures, validations et contrôles de révision restent directs en base. Les clés séparent les équipes et changent aux minuits UTC et Maurice. Aucun échec, résultat absent ni valeur expirée n’est utilisé comme secours hors ligne. Les réponses HTTP restent `no-store` et aucun stockage navigateur n’est ajouté.

Ce cache est borné (256 entrées métier, 64 publiques) et partagé entre les requêtes **d’une même instance serveur**, pas entre plusieurs instances Vercel/processus. Une modification depuis une autre instance ou directement en base peut donc rester invisible jusqu’à 5 secondes (60 secondes pour les métadonnées publiques). Aucun service de cache distribué ni migration supplémentaire n’est requis ; Neon reste la source durable de vérité.

Les chargements de route, de l’équipe, des questions et du baromètre affichent des **squelettes statiques** adaptés à la page : pas de shimmer, animation infinie ou temporisation artificielle. Les erreurs Neon gardent leurs messages et boutons de nouvelle tentative ; un squelette ne remplace jamais une panne ni les gardes de validation.

Les lectures indépendantes équipe/historique et catalogue/baromètre quotidien démarrent en parallèle. Le minuteur n’installe aucun intervalle en préparation ou en pause ; pendant la parole, quatre rafraîchissements par seconde remplacent les dix précédents. Les échéances restent la source du temps, et chaque action mesure exactement le temps écoulé avant de modifier le décompte. L’observation des animations est limitée aux attributs utiles et aux listes, sans observer les mutations de texte du compte à rebours.

Les métadonnées publiques des baromètres ont un cache **en mémoire seulement**, 60 secondes pour le catalogue et cinq minutes pour au plus 20 présentations. Les échecs et requêtes annulées ne sont pas mémorisés ; les données d’équipe, les votes et l’historique ne sont pas mis en cache par ce mécanisme. Les images utilisent le décodage asynchrone. Le spectateur ne fait pas de requêtes ni de rafraîchissements de temps lorsque son onglet est caché et resynchronise immédiatement au retour ; la diffusion du facilitateur conserve son renouvellement pour ne pas interrompre un direct en cours.

Le test [loading_performance_smoke](tests/loading_performance_smoke.py) retarde volontairement les réponses pour vérifier les squelettes, les erreurs/reprises, les lectures parallèles et le nombre réel de mises à jour du minuteur. Ces mesures locales ne constituent pas une promesse de latence en production : Neon, le proxy, Google, Redis et le réseau des utilisateurs restent des dépendances externes.

### Télécommande mobile par QR code

**Commandes complémentaires :** **Redémarrer** ouvre une confirmation Oui/Non pour le passage actuel uniquement : le décompte revient à sa durée initiale, en pause, sans effacer le temps déjà parlé ni les pénalités. Le démarrage suivant compte comme une relance selon le barème existant. **Pénalité** retire **50 points par clic**, de façon cumulative, après le calcul temps/relances et avec un score final minimum de zéro ; la déduction est incluse dans le score enregistré et conservée lors d’une récupération dans le même onglet. **Écran noir** masque l’affichage de l’ordinateur maître et met le minuteur en pause ; **Rétablir l’écran** (ou un clic/Échap sur l’ordinateur) dévoile l’affichage sans reprendre automatiquement. La vue spectateur n’est pas masquée. Pendant l’écran noir, seule la restauration reste disponible à distance. Les commandes attendent un nouvel état confirmé par le maître avant d’être réactivées.

**Proposition d’installation :** une fenêtre s’ouvre au chargement du compagnon dans le navigateur. **Ne plus afficher automatiquement** mémorise uniquement une préférence d’interface sous `standup.companion.install.hidden.v1`, séparée de l’association d’équipe. Si le stockage est bloqué, une notice le signale et le choix reste limité à la page courante. **Ajouter l’application** permet de rouvrir la fenêtre. Une application déjà ouverte en mode autonome ne reçoit pas cette proposition.

Sur le minuteur, le bouton **Télécommande mobile** (icône téléphone) ouvre **Activer le QR de l’équipe**. Chaque équipe possède **un seul lien/QR réutilisable**, identique d’un point à l’autre tant que son identifiant et le secret serveur ne changent pas. Scannez-le avec l’appareil photo du téléphone : le lien ouvre la route compagnon `/remote`, sans introduction ni navigation d’équipe. Fermez ensuite la fenêtre QR sur l’ordinateur pour autoriser les commandes. Le compagnon est une **télécommande de présentation avec un décompte compact, sans anneau de minuteur** : personne active centrée, pastilles de temps et d’état, grand pavé démarrer/reprendre/pause et commande orange de passage suivant avec la prochaine personne. La disposition verticale reste centrée et de largeur limitée sur tablette/ordinateur, avec des cibles tactiles généreuses, un défilement possible sur écran court et une fenêtre d’installation. Le décompte synchronisé reste secondaire aux commandes et affiche le dépassement ; hors connexion, il est remplacé par un indicateur indisponible. Une confirmation devient caduque si l’état du minuteur change. Aucun passage automatique à zéro, aucune modification des humeurs ou des réglages depuis le téléphone. Le bouton précédent est remplacé par le redémarrage confirmé du passage actuel.

Le minuteur de l’ordinateur reste la source de vérité : gardez son onglet ouvert et visible. Les fenêtres de gestion suspendent les commandes distantes, sans modifier le comportement local du décompte. Un état déconnecté désactive les commandes ; aucune commande de plus de cinq secondes n’est exécutée au retour. Le serveur vérifie l’état et sa version, limite à une commande en attente et sépare les capacités propriétaire/contrôle. Le QR est généré localement, sans service d’image externe ; sa capacité HMAC reste dans le fragment du lien et passe à l’API uniquement par en-tête Bearer. Le transport ne conserve que les empreintes des capacités. Toute personne disposant du lien peut contrôler cette équipe lorsque la télécommande est activée : ne le publiez pas. **Désactiver** arrête la session de contrôle mais **ne révoque pas le QR permanent**. Les téléphones attendent la prochaine activation avec le même lien. La session serveur expire après quatre heures au maximum ; un autre ordinateur ne peut la remplacer tant que sa courte présence est renouvelée. Après fermeture brutale, attendez dix secondes avant de reprendre depuis un autre ordinateur. La rotation du secret serveur invalide tous les QR concernés ; aucune révocation individuelle n’est proposée.

**Installer sur le téléphone :** en HTTPS, utilisez **Installer** lorsque le navigateur le propose, ou **Ajouter à l’écran d’accueil**. Sur iPhone/iPad, ouvrez Safari → Partager → **Sur l’écran d’accueil** ; sur Android, utilisez le menu **Installer l’application** ou **Ajouter à l’écran d’accueil**. L’app s’ouvre en mode autonome avec son icône. L’association d’équipe (identifiant et capacité de contrôle uniquement) est mémorisée dans le `localStorage` du téléphone pour retrouver l’équipe depuis l’icône, sans conserver de temps, progression, roster ou identifiant propriétaire. Cette exception est limitée au compagnon ; la persistance métier du maître reste inchangée. Un stockage bloqué affiche une notice et nécessite de conserver le lien ou rescanner. **Oublier cette équipe sur ce téléphone** supprime cette association. Certains systèmes isolent le stockage de l’app installée : dans ce cas, rescanner le même QR peut être nécessaire. Le manifeste ne contient aucun secret, et le service worker est limité au compagnon, ne met aucune API ni commande en cache et affiche une erreur explicite hors connexion. L’installation n’offre pas de contrôle hors ligne.

**Déploiement du compagnon :** configurez un secret serveur stable `TIMER_REMOTE_SECRET` d’au moins **32 octets UTF-8**, sans préfixe `NEXT_PUBLIC_`, identique sur toutes les instances. À défaut, `PARTICIPANT_PORTAL_SECRET` est utilisé s’il est configuré ; changer ce secret change les QR. Sans secret valide, l’activation échoue explicitement (503), sans lien temporaire de secours. Sur Vercel ou tout hébergement multi-instance, configurez également côté serveur maître **l’un des deux transports Redis** :

- **Redis natif :** `REDIS_URL`, avec une URL `redis://` ou `rediss://` (TLS), via le client officiel `@redis/client`. Une intégration Redis Vercel qui fournit `REDIS_URL` convient ; Upstash n’est pas requis pour le compagnon.
- **Alternative Upstash REST :** `UPSTASH_REDIS_REST_URL` (HTTPS) **et** `UPSTASH_REDIS_REST_TOKEN`. Cette configuration existante reste valide et prend explicitement priorité sur `REDIS_URL` dès qu’une des deux variables REST est renseignée. Une paire REST incomplète échoue, même si `REDIS_URL` est présent : aucun repli vers Redis natif ou la mémoire.

Les deux transports exécutent les **mêmes opérations atomiques Lua** et les entrées de session expirent automatiquement, sans table Neon ni migration. Une configuration invalide ou un transport indisponible provoque une erreur explicite, jamais un repli silencieux vers un autre transport ou la mémoire. Sans configuration Redis, le mode **serveur unique** fonctionne uniquement hors Vercel si les deux appareils atteignent le même processus ; il n’est pas fiable sur un déploiement serverless. **Cette prise en charge de `REDIS_URL` concerne uniquement le compagnon : le canal de diffusion spectateur reste limité à Upstash REST pour le transport partagé**, comme indiqué dans « Déploiement du direct ».

Utilisez l’origine HTTPS déployée pour le contrôle et l’installation sur téléphone. En développement, `localhost` sur le téléphone désigne le téléphone lui-même : ouvrez le site sur l’ordinateur via son adresse LAN accessible aux deux appareils avant de créer le QR, et autorisez uniquement le trafic réseau nécessaire. Le contrôle peut fonctionner en HTTP LAN, mais l’installation nécessite HTTPS. Le lien ne doit pas être réécrit par un service tiers.

Les [tests de télécommande](tests/timer-remote.test.ts) couvrent validations, capacités, isolation, expiration, concurrence, réutilisation et adaptateurs. Le [test navigateur mobile](tests/timer_remote_smoke.py) couvre QR, deux contextes ordinateur/téléphone, démarrage/pause, confirmation/annulation, déconnexion/reprise, réactivation du même lien, mémorisation/oubli et six formats dans les deux modes de mouvement avec API simulées. Les [tests PWA](tests/companion-pwa.test.ts) et le [smoke d’installation](tests/companion_install_smoke.py) couvrent manifeste, icônes PNG, service worker réseau uniquement, invitation synthétique et mode autonome. Ils ne prouvent pas la configuration Redis réelle, l’installation native sur téléphone ni la lecture du QR par un appareil photo physique.

#### Vercel : configuration et latence

Dans **Vercel → projet maître → Settings → Environment Variables**, configurez `TIMER_REMOTE_SECRET` et soit `REDIS_URL`, soit la paire `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`, puis redéployez. Les variables sont **propres à chaque environnement** : une valeur Production n’est pas automatiquement disponible en Preview. Pour chaque environnement utilisé, vérifiez la portée de l’intégration Redis et des variables, ainsi que la correspondance du secret entre les instances qui doivent communiquer ; le maître et le téléphone doivent utiliser le même déploiement. Ne transmettez jamais les valeurs secrètes dans une conversation.

**Dans votre configuration déclarée, l’intégration Redis fournit déjà `REDIS_URL` et `TIMER_REMOTE_SECRET` est configuré en Production : il suffit de déployer le code mis à jour pour le compagnon, sans ajouter Upstash.** Vérifiez seulement qu’aucune variable REST résiduelle ne sélectionne prioritairement ce transport ; une configuration REST partielle bloque l’activation, sans repli sur `REDIS_URL`. Preview nécessite sa propre configuration si vous l’utilisez. Ces indications ne constituent pas une vérification en direct de la configuration, de la connexion Redis ou du déploiement de production.

Sur Vercel (`VERCEL=1`), l’absence de Redis produit une erreur 503 : la mémoire d’une fonction n’est pas un transport entre appareils. Le mode serveur unique reste réservé au développement hors Vercel.

Placez la **région d’exécution des fonctions Vercel** au plus près de la **région primaire de Redis**, idéalement dans la même région, en tenant aussi compte de Neon pour les autres routes. Vérifiez ces régions dans les tableaux de bord avant de les modifier ; aucune région n’est imposée arbitrairement par le code. Après changement de configuration, redéployez. Une fonction froide, une région distante ou le réseau mobile peuvent ajouter de la latence ; installer la PWA ne supprime pas ces trajets.

Le maître relève les commandes toutes les **350 ms**, le téléphone lit l’état toutes les **500 ms**, sans requêtes simultanées sur chaque canal. Un changement de personne, pause/reprise ou fenêtre publie immédiatement l’état (les changements en vol sont regroupés), et la réception d’une commande déclenche immédiatement sa confirmation. Ce polling vise une réponse plus rapide, **pas une garantie temps réel** : deux navigateurs actifs génèrent environ 291 requêtes/minute hors actions, avec des coûts d’invocations et Redis à surveiller. Les lectures s’arrêtent lorsque le téléphone est masqué. Aucune commande n’est appliquée optimistiquement sur le téléphone.

Pour diagnostiquer : ouvrez les outils réseau du navigateur et filtrez `/api/timer-remote`. L’en-tête **`Server-Timing: remote;dur=…`** mesure le traitement de la route après son entrée (transport Redis inclus, pas le démarrage à froid ni le trajet navigateur). Comparez-le à la durée réseau totale et aux journaux/régions Vercel. Le téléphone affiche une notice si l’aller-retour de lecture dépasse une seconde ; le décompte utilise une estimation de demi-trajet, sans garantie de synchronisation parfaite. Les tests locaux instrumentés mesurent l’attente ajoutée par l’interface avec des API simulées ; ils ne mesurent pas votre déploiement réel.

### Direct, présentation et questions

- Sur le minuteur, **Diffusion** ouvre les commandes : **Diffuser en direct**, **Lien spectateur** et **Présentation**. La diffusion est volontaire ; le lien `/spectator?team=…` ouvre une vue sans commandes de réunion ni navigation d’édition. Elle affiche la personne active, la suivante, le temps et les passages terminés, jamais les humeurs ni les tickets. Les équipes ordinaires restent partagées sans authentification ; les équipes sprint exigent la connexion Jira et l’accès au tableau, même pour lire le direct.
- Le facilitateur reste seul maître de son minuteur. Une possession temporaire empêche deux diffuseurs de remplacer simultanément le direct de la même équipe. Les vues interrogent le direct toutes les deux secondes et calculent le décompte depuis une échéance alignée sur le serveur ; pause et dépassement sont conservés. Une perte de connexion masque le compte à rebours plutôt que de prétendre rester synchronisé.
- **Présentation** agrandit le minuteur dans un écran épuré et demande le plein écran du navigateur. **Quitter** ou Échap revient à la mise en page normale, sans réinitialiser le temps. Si le navigateur refuse le plein écran, la présentation reste disponible dans la fenêtre. La vue spectateur propose également ce mode.
- **Questions → Modifier** permet d’enregistrer 1 à 5 questions par équipe, de 160 caractères chacune, ou de rétablir les trois questions initiales. Les changements concurrents sont refusés avec une invitation à recharger ; ces réglages sont enregistrés dans Neon.
- Le bilan ne propose plus de questionnaire d’utilité ni de bouton « Avis ». Le classement, les scores, les statistiques et la réinitialisation restent disponibles. La migration [0008](drizzle/0008_remove_unused_round_feedback.sql) supprime définitivement les anciens retours et leur table ; l’API `/api/round-feedback` est retirée.

**Déploiement du direct :** sans configuration supplémentaire, le canal temporaire utilise la mémoire du processus Next.js, adaptée à un serveur local/une instance unique. Pour Vercel ou plusieurs instances, configurer côté serveur `UPSTASH_REDIS_REST_URL` (HTTPS) et `UPSTASH_REDIS_REST_TOKEN`. Ne jamais exposer le jeton via une variable `NEXT_PUBLIC_*`. Les écritures Redis sont atomiques, avec un TTL de 15 secondes renouvelé pendant la diffusion ; quitter la page ou arrêter le direct libère le canal. Redis ne sert ni d’archive ni de reprise de session : le facilitateur ne restaure jamais un compte à rebours depuis ce canal. Choisir un service Redis sans sauvegarde durable pour conserver cette garantie de données éphémères. L’interface signale explicitement la portée « serveur local uniquement » sans Redis partagé.

Appliquer toutes les migrations avec `npm run db:migrate` avant de déployer. Les questions personnalisées conservent leurs tables de réglages/révision et de questions ordonnées. Les tests [meeting-store](tests/meeting-store.test.ts) vérifient les migrations dans PGlite, l’isolation, les conflits et les remplacements ; [meeting_features_smoke](tests/meeting_features_smoke.py) couvre les interfaces sur mobile et ordinateur avec APIs simulées, sans écritures Neon réelles.

Les migrations [0007](drizzle/0007_remove_unused_workspace_selection.sql) et [0009](drizzle/0009_remove_unused_audit_timestamps.sql) retirent également les colonnes inutilisées `workspaces.selected_team_id`, `teams.updated_at` et `team_daily_meters.created_at`. Les équipes, participants, présences, humeurs, notes, scores, bilans et caches restent conservés. `npm run db:verify` contrôle les colonnes canoniques et les empreintes du journal Drizzle après application. Déployer le code correspondant après la migration : une ancienne instance peut encore référencer les colonnes supprimées.

### Mode Google SVG à la demande (par défaut)

Le lecteur utilise désormais une liste de **888 URLs de présentations**, dans [src/lib/remote-mood-catalog.json](src/lib/remote-mood-catalog.json), indépendante de l’ancien corpus local. Il ne télécharge plus les PowerPoint et ne publie plus les images locales au démarrage/build. Seuls le logo, le secours HTML et un indicateur de mode sont publiés. Les sources existantes ne sont pas supprimées.

Un indicateur de chargement apparaît pendant la lecture du catalogue, des diapositives et de leur image. Les présentations utilisées sont étiquetées et exclues du choix automatique ; elles restent disponibles en choix manuel, comme le baromètre original. Si une présentation ne peut pas être chargée, une invitation à choisir ou réessayer remplace son contenu ; si son image échoue après sélection, un secours visuel original peut apparaître. Repères du baromètre original : **1 = mauvaise humeur / énergie élevée ; 2 = mauvaise humeur / énergie basse ; 3 = bonne humeur / énergie basse ; 4 = bonne humeur / énergie élevée**. Ces repères ne décrivent pas nécessairement les présentations externes.

À la sélection d’un baromètre, les routes Next.js lisent les identifiants de diapositives du lecteur public Google, puis demandent chaque image via l’export SVG de Google. Le navigateur affiche le SVG dans une image, jamais en HTML injecté. Les résultats réutilisent ces mêmes URLs. Un cache mémoire borné à 32 Mo conserve les réponses au maximum cinq minutes lors des accès ; aucun SVG ou PPTX n’est enregistré sur disque. Un hébergeur peut appliquer son propre cache HTTP.

**Aucun PowerPoint, autre ordinateur Windows, service de conversion ou clé API Google n’est nécessaire.** Sur Windows, [scripts/fetch-google-slide.ps1](scripts/fetch-google-slide.ps1) utilise le proxy système et ses identifiants Windows si nécessaire. Sur Linux et les plateformes comme Vercel, les routes utilisent directement HTTPS. L’accès Internet à Google est indispensable ; les présentations privées/refusées ne sont pas contournées. Les routes limitent les requêtes au catalogue, jamais à une URL libre. Le SVG est servi avec une politique sandbox et sans scripts.

**Limite : les SVG exportés sont statiques. Les GIF et animations PowerPoint ne sont pas préservés.** Les images matricielles intégrées restent matricielles même dans un SVG ; le format ne garantit pas un fichier plus petit. La première ouverture dépend du temps de réponse Google. Son export public n’est pas une API contractuelle : quotas, permissions ou changements du lecteur peuvent interrompre le service.

Commandes : `npm run mood:catalog` régénère la liste depuis le rapport existant sans télécharger les présentations ; l’option `-- -Refresh` relit les liens publics de Google Sites sans télécharger les PowerPoint. Après une modification, reconstruire/redéployer. Pour retrouver le mode local animé, définir `MOOD_LOCAL_ASSETS=1` dans l’environnement ou dans le fichier de configuration local ignoré par Git, puis relancer `npm run dev` ou reconstruire. Ce mode republie les ressources locales volumineuses. Ne définir aucune ancienne variable `MOOD_SERVICE_*` : le service séparé a été retiré.

Il génère [public](public) : logo, HTML de secours, catalogue JSON issu du [catalogue exporté](mood-meters/catalog.js) et images de [mood-meters/slides](mood-meters/slides). Conserver les sources racine [infomil-logo.svg](infomil-logo.svg) et [mood-meter.html](mood-meter.html), requises par la publication. **Ne jamais publier les PowerPoint sources**, rapports ou métadonnées internes dans le répertoire public. Les [scripts](scripts) de téléchargement/export et [mood-meters](mood-meters) restent indépendants de React.

Le corpus comprend **888 présentations, environ 9,6 Go** : vérifier le budget de stockage, le nombre de fichiers, les limites d’upload/build et la bande passante de l’hébergeur avant de déployer. Les liens physiques économisent de l’espace local, pas le budget des ressources déployées. Ne supposez pas qu’un hébergement gratuit peut accueillir l’ensemble.

Utiliser uniquement les ressources dont les droits autorisent l’utilisation et la redistribution.

## Persistance et migration

**Neon est l’unique persistance durable faisant autorité** pour les participants (noms, présences et humeurs), les réglages, les baromètres utilisés et l’historique des tours terminés. L’application ne conserve ces données ni dans des cookies applicatifs, ni dans `localStorage`, ni dans IndexedDB. Le seul stockage navigateur de reprise est le point temporaire du minuteur dans `sessionStorage`, décrit ci-dessous : ce n’est ni une archive durable, ni un cache métier de secours hors ligne. Le contexte d’équipe est conservé dans le paramètre d’URL `team` : un rechargement restaure cette équipe après vérification dans la liste Neon. Un lien sans contexte ou un identifiant supprimé utilise l’équipe proposée par la base. Chacun peut choisir une équipe sans changer la sélection des autres visiteurs ; le lien peut aussi être partagé ou mis en favori. Chaque requête d’équipe exige son identifiant explicite, vérifié dans Neon.

Le minuteur conserve désormais un **point de reprise dans `sessionStorage`, par équipe et par onglet** : ordre, reports, personne active, passages terminés, temps actif, relances, pause et échéance absolue. Après actualisation, l’équipe et le bilan sont d’abord vérifiés dans Neon, puis ce contexte est restauré avant les gardes de navigation. Une échéance en cours continue à compter le temps passé hors de la page, dépassement compris ; une pause reste en pause. Aucun passage ne change automatiquement. Le point est invalidé au changement de journée à Maurice, à une modification du contexte d’équipe ou à un bilan du jour confirmé. Le stockage bloqué affiche un avertissement. Fermer l’onglet peut perdre ce contexte ; il n’est pas partagé entre appareils et ne remplace pas Neon. Les notifications/audio ne peuvent pas être garantis pendant la suspension ou la fermeture d’une page. Le miroir de diffusion n’est jamais utilisé pour la reprise. Les bilans confirmés restent dans Neon pendant 5 jours civils UTC, aujourd’hui inclus.

**Aucun import automatique des anciennes données navigateur n’est effectué**, même sur la même origine. Les anciennes clés ne sont ni lues ni effacées automatiquement. Les données de l’ancien site, y compris sous `file://`, ne sont donc pas reprises dans Neon ; une éventuelle migration explicite est une opération distincte, non incluse dans le démarrage.

### Équipes et baromètre quotidien

Si le CLI standard ne peut pas ouvrir sa connexion WebSocket sur le réseau Windows, l’opérateur peut exécuter explicitement `npx tsx scripts/migrate-http.ts` : ce script utilise le migrateur HTTP officiel de Drizzle, les mêmes fichiers et le même journal, avec le proxy système existant. `npm run db:migrate` reste le CLI standard. Cette solution n’est jamais déclenchée par une requête utilisateur ; vérifier ensuite avec `npm run db:verify`.

**Chargement automatique du catalogue :** si Neon ne contient aucun baromètre distant, ou si la période de sept jours est expirée, le serveur relit la page publique SCRED, extrait toutes les présentations et leurs catégories, puis les enregistre atomiquement avant de répondre au menu déroulant. Les chargements suivants lisent Neon sans refaire cet appel source. Les nouvelles présentations sont sélectionnables sans reconstruction ; les identifiants déjà publiés sont conservés. Les liens historiques absents de la page restent disponibles sous « Autres ». Si la source échoue ou renvoie une page incomplète, aucune liste partielle n’est enregistrée et l’ancien cache n’est pas effacé. La migration 0003 doit déjà être appliquée : une table manquante n’est pas une table vide et n’est jamais créée lors d’une requête utilisateur.

Le catalogue distant (identifiants Google, titres et catégories) et les listes de diapositives résolues sont partagés dans Neon via trois tables de cache dédiées : `remote_mood_cache_state`, `remote_mood_catalog` et `remote_mood_pages`. Appliquer la migration [0003](drizzle/0003_remote_mood_cache.sql) avec `npm run db:migrate` avant de déployer cette version. Au premier accès, la source publique initialise le cache ; chaque présentation est ensuite chargée à la demande. **Après sept jours, la première requête suivante récupère et valide la source avant toute suppression ; si cette lecture réussit, le catalogue expiré et ses listes de diapositives sont remplacés atomiquement.** Si la source échoue, les anciennes lignes restent en base, sans être servies comme secours expiré. Ce renouvellement est effectué à la demande, sans tâche planifiée pendant que le site est inutilisé. Les autres visiteurs et instances réutilisent les URL enregistrées ; une nouvelle génération empêche une récupération de diapositives commencée avant le renouvellement de réinsérer les anciennes URL. Les équipes, participants, votes, choix quotidiens et historiques ne sont jamais supprimés par ce renouvellement. Les SVG eux-mêmes restent récupérés à la demande avec un cache mémoire borné de cinq minutes, sans stockage des images ou des PowerPoints en base. Une panne de Google ne laisse pas de liste partielle en base ; une panne de Neon est signalée, sans cache navigateur de remplacement. Voir [le cache du catalogue](src/lib/mood-fetch-cache.ts).

Le catalogue reprend les **12 catégories du site SCRED**, affichées en français dans des groupes du menu déroulant avec leur nombre de baromètres. Les titres et identifiants restent inchangés ; les entrées absentes de la page source apparaissent sous « Autres ». Les catégories sont chargées depuis les titres de sections publics, pas déduites des noms. Pour actualiser uniquement les métadonnées du catalogue embarqué sans télécharger de présentations ni modifier le corpus PowerPoint : `npm run mood:catalog -- -CategoriesOnly`, puis reconstruire et redéployer. Une panne de la source pendant cette commande laisse le fichier existant intact. Cette opération est distincte du renouvellement automatique du cache Neon : la navigation lit ce cache tant qu’il est valide, puis sollicite à nouveau SCRED à son expiration.

Le sélecteur dans la barre de navigation permet de **rechercher, créer et choisir une équipe**, sans limite applicative sur le nombre d’équipes. Toutes les équipes et leurs participants sont accessibles à tous les visiteurs du même site, y compris sur un nouveau téléphone. Chaque équipe conserve ses propres membres, présences, humeurs, réglages et statistiques. Le choix d’équipe reste indépendant par navigateur. Après création/sélection, le parcours revient à Participants. Une sauvegarde en attente bloque le changement d’équipe. Les requêtes portent explicitement l’identifiant de l’équipe partagée.

Chaque équipe utilise **un baromètre partagé par jour civil à Maurice** (`Indian/Mauritius`, UTC+4). **Avant le premier vote**, chaque ouverture ou rechargement des Humeurs choisit aléatoirement un autre baromètre non utilisé, confirmé dans Neon avant de voter. Le catalogue et le bouton aléatoire restent disponibles pour un choix manuel. Si aucun autre baromètre non utilisé ne reste, le choix partagé existant est conservé ; à la première initialisation sans candidat, l’original est utilisé. Le premier vote ou un bilan terminé verrouille le baromètre, y compris après rechargement, pour éviter de mélanger des repères différents. Le serveur impose cette règle sous verrou d’équipe, y compris entre appareils ; un vote concurrent conserve le choix verrouillé. Les check-ins précédents doivent être renseignés à nouveau le jour suivant. Les decks indisponibles peuvent être réessayés ou remplacés avant le premier vote.

La migration [0002](drizzle/0002_workspace_daily_meters.sql) ajoute `workspaces`, les noms/appartenances historiques des équipes et `team_daily_meters`, avec une clé unique équipe–date. Les anciennes données et références sont conservées ; les anciennes sélections privées ne sont plus lues ni modifiées. Un seul espace commun en base sert aux nouvelles équipes, sans créer d’espace par visiteur. Les douze tables restent relationnelles sans colonne JSON ; les limitations physiques de l’hébergement continuent à s’appliquer.

### Neon : configuration privée

La variable serveur `DATABASE_URL` se place dans le fichier d’environnement racine **.env**, ignoré par Git. Ne jamais y committer des identifiants ; si le mot de passe a été partagé dans une conversation, le renouveler dans Neon et remplacer la valeur locale. L’ancienne variable `COOKIE_SECURE` n’est plus utilisée.

Le classement historique de l’onglet **Statistiques du portail participants** regroupe les participants par identifiant stable sur les 5 jours civils UTC, aujourd’hui inclus. Le rang dépend du **score moyen / 1 000** des passages mesurés, pas du nombre de participations ; les égalités partagent le rang et les passages non mesurés restent sans score. Noms récents, nombre de passages et durée moyenne sont affichés dans une liste compacte paginée par huit. Le classement du tour courant reste disponible à la fin du minuteur maître. Les humeurs ne modifient aucun score.

Dans **Neon → Connect**, sélectionner l’endpoint **ep-little-cloud-aojwgz1g**, puis copier sa **chaîne de connexion PostgreSQL complète avec pooler et TLS**. Le nom d’endpoint seul ne contient ni la région, ni le rôle, ni le mot de passe : il ne suffit pas pour se connecter. Ajouter cette chaîne comme variable serveur **`DATABASE_URL`** dans la configuration locale ignorée par Git et dans les variables de l’hébergeur, puis redémarrer/redéployer. Ne jamais la préfixer par `NEXT_PUBLIC_`, la publier ou la transmettre dans le chat.

La persistance utilise **Drizzle ORM avec le pilote Neon HTTP**, avec des tables relationnelles normalisées et **aucune colonne JSON/JSONB persistée**. Le [schéma typé](src/db/schema.ts) définit :

| Table | Responsabilité |
| --- | --- |
| teams | Équipe partagée, espace de création historique, réglages, révision optimiste et jeton transactionnel. |
| participants | Identité et nom courant ; conservés si un historique les référence. |
| team_members | Appartenance à la liste active, position et présence. |
| participant_check_ins | Humeur, date PostgreSQL avec fuseau et références de diapositive. |
| mood_meters / mood_meter_identifiers | Titres historiques et identifiants de catalogue distincts : un titre seul ne prouve pas l’identité d’un deck. |
| mood_meter_slides | Contexte de diapositive unique, lié au baromètre. |
| team_used_mood_meters | Association équipe–baromètre utilisé et ordre. |
| standup_sessions / speaking_turns | Sessions terminées et passages individuels ; le nom au moment du passage reste une valeur historique. |

Clés primaires/composites, clés étrangères, contraintes d’unicité et `CHECK` imposent l’intégrité. Toutes les références sont isolées par équipe privée. Les écritures de profil et de leurs lignes associées sont atomiques via `db.batch`, avec une révision et un jeton de transaction qui empêchent un onglet périmé de modifier les enfants. Les sessions terminées sont idempotentes. Le JSON n’est utilisé que pour le transport HTTP et les paramètres/résultats SQL, jamais comme stockage. Aucun PowerPoint, SVG ou GIF n’est stocké dans Neon. Adaptateurs : [src/lib/database.ts](src/lib/database.ts), [src/lib/relational-store.ts](src/lib/relational-store.ts). Routes : [src/app/api/team/route.ts](src/app/api/team/route.ts) et [src/app/api/history/route.ts](src/app/api/history/route.ts).

**Avant de démarrer ou déployer**, exécuter `npm run db:migrate` avec `DATABASE_URL` configurée. Cette commande lance désormais **`drizzle-kit migrate`**, sans runner personnalisé. Les tables ne sont plus créées lors des requêtes utilisateur. La [configuration Drizzle](drizzle.config.ts) charge les variables avec le chargeur Next.js (les configurations locales prioritaires peuvent remplacer la valeur racine) et conserve explicitement le journal existant `drizzle.__drizzle_migrations` : les migrations déjà appliquées ne sont pas rejouées. Ne pas utiliser de commande destructive de type push/reset sur une base existante. Après modification du schéma : `npm run db:generate`, examiner le SQL généré, `npm run db:check`, puis `npm run db:migrate`. Le rôle de migration doit pouvoir créer tables/index et le journal Drizzle ; en production le rôle applicatif peut être limité aux lectures/écritures. Les erreurs du CLI peuvent inclure des détails de connexion ; ne pas publier ses journaux sans les examiner et les expurger.

La migration initiale adopte les anciennes tables. La [migration relationnelle](drizzle/0001_abandoned_snowbird.sql) verrouille ces tables, convertit leurs profils et **tous** leurs historiques (sans appliquer la rétention pendant la conversion), compare les champs et les nombres de lignes, puis supprime les anciennes tables JSON seulement après vérification. Une valeur non prise en charge annule la transaction complète. Le migrateur PostgreSQL de Drizzle utilise une transaction pour les migrations en attente et leurs entrées de journal ; arrêter les anciens serveurs avant migration et déployer la nouvelle version ensuite. Effectuer également une sauvegarde/branche Neon suivant les procédures de l’hébergeur avant une migration de production. `npm run db:verify` vérifie les douze tables et l’absence de colonnes JSON. Un code `UND_ERR_CONNECT_TIMEOUT` ou `ENOTFOUND` signale un problème réseau, pas une migration réussie ; ne jamais désactiver TLS.

Les actions sont validées côté interface, au fournisseur d’état et à l’API : noms de 1 à 60 caractères après suppression des espaces extérieurs, sans caractères de contrôle ; maximum 100 personnes ; humeurs 1–4, identifiants uniques et réglages bornés. Les noms sont toujours du texte React, jamais du HTML injecté. Le bouton de modification conserve l’identité, la présence et l’humeur. Les suppressions individuelles et groupées demandent confirmation. Les entrées invalides sont rejetées, pas tronquées silencieusement. Les [tests de base](tests/database.test.ts) exécutent la migration et les écritures dans PostgreSQL isolé via PGlite, sans accès à Neon.

**Proxy Windows avec les identifiants actuels** : [src/lib/neon-network.ts](src/lib/neon-network.ts) configure le pilote Neon HTTP pour utiliser [scripts/neon-proxy-request.ps1](scripts/neon-proxy-request.ps1), le proxy système et `ProxyUseDefaultCredentials`. Aucun mot de passe Windows n’est demandé ni stocké. La connexion Neon, ses en-têtes et les requêtes SQL transitent uniquement par stdin vers PowerShell (ni arguments de processus, ni fichiers temporaires, ni journaux). TLS reste vérifié ; redirections refusées, délais et tailles bornés. Sur Linux/Vercel, le pilote conserve HTTPS natif. **Seuls l’application et `npm run db:verify` partagent cet adaptateur HTTP.** `npm run db:migrate` / `npx drizzle-kit migrate` utilise le pilote WebSocket Neon et nécessite un accès DNS/WebSocket autorisé vers Neon ; il ne bénéficie pas automatiquement des identifiants du proxy Windows. Sur ce poste, l’essai du CLI a échoué avec `ENOTFOUND` avant l’application de SQL de migration. Exécuter les migrations depuis un environnement réseau autorisé (par exemple CI), sans désactiver TLS. Les trois migrations précédemment appliquées restent enregistrées ; la vérification HTTP confirme douze tables applicatives sans colonne JSON. Le script PowerShell doit être présent au déploiement Windows de l’application, et le compte qui exécute Node doit disposer de l’accès proxy autorisé.

**Équipes ordinaires : accès partagé sans compte.** Tous les visiteurs du même déploiement peuvent voir et modifier leurs participants, humeurs et bilans, et réinitialiser le point du jour après confirmation. Les anciennes équipes restent ordinaires, sans copie ni conversion. Les anciens cookies de sélection sont ignorés ; les cookies de connexion Jira concernent uniquement les accès sprint. Protéger le déploiement par un contrôle externe si les données ordinaires doivent rester internes. Les équipes sprint exigent séparément une session Jira et l’accès au tableau lié. À chaque lecture ou enregistrement d’historique d’une équipe, les sessions antérieures à minuit UTC quatre jours avant aujourd’hui sont supprimées de Neon, avec leurs passages individuels en cascade. Les équipes, participants et résultats des cinq jours conservés ne sont pas supprimés. Le nettoyage est effectué à la demande, sans tâche planifiée ni nouvelle migration pour ce changement de durée.

**Un seul point quotidien terminé par équipe et par jour à Maurice.** Les fins de tour sont sérialisées sous verrou d’équipe ; une deuxième fin différente est refusée, les retransmissions du même bilan restent idempotentes. Le bilan du jour est chargé avant le parcours. Les Humeurs et le Minuteur proposent **Voir le bilan du jour** ou **Réinitialiser aujourd’hui**. Participants reste accessible avec un lien vers ces choix. Après confirmation, réinitialiser supprime les résultats et humeurs du jour pour tous les appareils, mais conserve les équipes, participants, jours précédents et baromètre du jour. Les anciennes révisions de profil sont invalidées. Aucune nouvelle migration n’est nécessaire.

Le fournisseur attend une **lecture Neon réussie** avant de débloquer le parcours et les gardes de route. Une configuration absente ou une base inaccessible bloque clairement le démarrage ; une base vide ne déclenche aucun import local. Un conflit de version entre appareils ne remplace pas silencieusement les profils. L’API limite et valide les données et refuse les écritures cross-origin. Le partage entre navigateurs utilise la même base Neon ; seule une équipe sprint nécessite l’authentification Jira.

Les chargements d’équipe et les sauvegardes équipe/bilan échouant pour une erreur réseau, un délai dépassé, HTTP 408/425/429 ou 5xx sont **retentés automatiquement sans limite de nombre**, après 1, 2, 4, 8, 16 puis 30 secondes maximum entre essais (un `Retry-After` explicite peut imposer plus). Le retour du réseau ou de l’onglet déclenche une reprise immédiate. Une seule chaîne d’écriture est active. Les erreurs de validation/autorisation et les vrais conflits 409 ne sont pas retentés aveuglément. Une réponse PUT perdue est réconciliée avec le contenu autoritaire avant d’avancer sa révision ; un autre contenu reste bloqué pour éviter un écrasement. Les créations/suppressions ne sont pas rejouées automatiquement. Les autres éditeurs spécialisés gardent leur gestion explicite des erreurs.

Les modifications d’équipe en attente restent **uniquement en mémoire** ; ce n’est pas un mode hors ligne. Un avertissement `beforeunload` signale leur perte possible en quittant ou rechargeant. Le point de reprise du minuteur permet aussi de renvoyer un bilan terminé non confirmé avec le même identifiant, tant que son contexte reste valide, mais seuls les enregistrements confirmés par Neon sont durables. Une actualisation pendant une panne Neon attend le retour de la base avant d’ouvrir le minuteur. Effacer les données du navigateur ne supprime aucune donnée Neon.

### Personnes présentes mais pas encore arrivées

Dans le bilan d’humeur, **Plus tard** reporte explicitement l’humeur et le passage d’une personne sans la marquer absente. Au moins une personne doit avoir voté et être prête pour commencer. Le minuteur ignore les personnes en attente lors de **Suivant** ; elles ne sont jamais marquées comme ayant terminé. Le mélange est réservé à la préparation depuis Participants et inclut toutes les personnes présentes. **↷ Reporter** permet également de reporter un passage, y compris celui en cours : le décompte s’arrête et les secondes déjà utilisées sont conservées.

**Nouveau bilan**, après confirmation sur Participants, vide `postponed`, `session` et `currentMoodSlide`, efface toutes les humeurs, leurs dates et leurs références de diapositive, puis marque tout le monde présent. Annuler conserve le tour et son point de reprise. Tout changement de présence retire le report de la personne concernée sans effacer son humeur existante : une personne remise présente sans humeur doit voter ou être reportée explicitement à nouveau. Ces transformations sont centralisées dans [les helpers de présence](src/lib/attendance.ts). Le [fournisseur d’équipe](src/providers/team-provider.tsx) efface immédiatement le point de reprise dans `sessionStorage` et son miroir en mémoire lorsque le contexte de reprise change ou qu’une session non vide est vidée ; rétablir ensuite les anciennes présences ne ressuscite donc pas l’ancien tour. Ne pas confondre **Nouveau bilan** avec **Réinitialiser aujourd’hui**, qui supprime le bilan partagé du jour après confirmation.

À leur arrivée, utiliser **Renseigner les humeurs** dans la fenêtre Participants, dans **Modifier**, ou dans la fenêtre proposée après le dernier passage disponible (via **Suivant**, sans changement automatique à zéro). Cette action met le décompte en pause et ouvre une fenêtre sur le minuteur, sans quitter la page. Le même baromètre attribué reste verrouillé et ses diapositives SVG sont affichées ensemble ; aucun nouveau tirage n’est effectué. Seules les personnes encore reportées y votent et rejoignent la fin du tour. **Revenir au tour** conserve l’ordre, les passages terminés et le temps déjà utilisé, sans démarrage automatique. Ce fonctionnement reste disponible si le stockage de session est bloqué ; la reprise après actualisation exige ce stockage. On peut aussi **Terminer sans les personnes en attente** : seuls les passages non reportés sont archivés, sans marquer les autres absentes ni leur attribuer un passage ou un score. Au moins un passage terminé est nécessaire pour enregistrer un bilan. Seules les humeurs et les bilans confirmés sont sauvegardés dans Neon.

Les listes affichent une barre de pagination à droite : flèche vers le haut pour **Page précédente**, flèche vers le bas pour **Page suivante**, et numéro de page entre les deux. Le changement de page glisse verticalement, sans animation si la réduction des mouvements est activée. La barre disparaît lorsqu’une seule page suffit. La fonctionnalité « Vue d’ensemble » a été supprimée.

### Plein écran et lecture du baromètre

Sur ordinateur (largeur d’au moins 1024 px avec pointeur précis), une invitation propose **Entrer en plein écran** ou **Continuer sans plein écran**. Le plein écran reste facultatif : Échap ou un clic hors de la fenêtre ferme également l’invitation. Après acceptation ou fermeture, elle ne réapparaît pas pendant la navigation ni en quittant le plein écran ; un rechargement peut la proposer de nouveau. Le bouton **Présentation** permet de l’activer plus tard. Quitter un plein écran actif met toujours un minuteur en cours en pause. Les téléphones, les tablettes tactiles, la télécommande et la vue spectateur ne sont pas soumis à cette invitation. Si l’API est indisponible ou si l’autorisation est refusée, une explication apparaît et l’option de continuer sans plein écran reste disponible.

Les SVG du baromètre s’affichent l’un sous l’autre sur tous les écrans. Les pages utilisent toute la largeur de la fenêtre, avec une marge intérieure adaptée à la taille de l’écran. **Agrandir le baromètre** ouvre un lecteur occupant toute la fenêtre, avec un bouton par diapositive et une fermeture explicite. Il reste disponible dans la fenêtre des personnes reportées, sans changer le baromètre attribué ni l’humeur enregistrée. Le plein écran du navigateur porte sur le document entier afin de conserver les fenêtres de notes, de réglages et d’humeur visibles.
