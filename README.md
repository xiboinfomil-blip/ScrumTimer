# Infomil Mauritius — Point quotidien

Application Next.js App Router, React, TypeScript et **Tailwind CSS v4**, migrée depuis le site HTML/JavaScript. L’interface et les comportements restent en français. L’ouverture directe de fichiers locaux (`file://`) n’est plus prise en charge : utilisez le serveur Next.js.

## Installation et commandes

Node.js **>= 20.9** et npm sont nécessaires. Depuis la racine du projet :

| Commande | Usage |
| --- | --- |
| `npm install` | Installer les dépendances. |
| `npm run dev` | Préparer les ressources puis lancer le développement sur http://localhost:3000. |
| `npm run build` | Préparer les ressources puis créer le build de production. |
| `npm run start` | Servir un build de production existant. |
| `npm run lint` | Vérifier les règles ESLint. |
| `npm run typecheck` | Vérifier TypeScript sans émission. |
| `npm run test` | Lancer le runner Node sur les tests TypeScript ; nécessite une version de Node prenant en charge `--experimental-strip-types` (Node >= 22.6). |
| `npm run assets` | Republier les ressources navigateur dans [public](public). |
| `npm run db:generate` | Générer une migration Drizzle après modification du schéma. |
| `npm run db:check` | Vérifier la cohérence des migrations Drizzle. |
| `npm run db:verify` | Vérifier la connexion Neon, les tables et le journal Drizzle sans afficher de données privées. |
| `npm run db:migrate` | Appliquer les migrations versionnées à Neon avant le déploiement. |

Les [tests de domaine](tests/domain.test.ts) couvrent la normalisation, les transformations de données, les prérequis de session, le mélange, les échéances et les chemins du catalogue ; ils ne prouvent pas un import automatique d’anciennes données navigateur. Node 22.6+ est conseillé pour utiliser toutes les commandes, même si le minimum de l’application est 20.9.

### Page sans styles ou bloquée sur le chargement

Pour modifier l’interface, privilégiez `npm run dev` : les changements sont actualisés automatiquement. Un serveur lancé avec `npm run start` utilise le build chargé à son démarrage. **Arrêtez tous les serveurs de production de ce projet avant `npm run build`, puis redémarrez-les une fois le build terminé.** Sinon, les anciennes pages peuvent demander des fichiers CSS/JavaScript remplacés et recevoir des erreurs HTTP 500.

Après le redémarrage, rechargez la page (Ctrl+F5 si nécessaire). Les données métier sont exclusivement dans Neon et partagées entre tous les appareils du même déploiement. Aucun cookie applicatif ni stockage navigateur n’est nécessaire.

## Parcours et comportement

- **`/teams`** : écran de démarrage avec recherche des équipes, ouverture, accès à la gestion et création. La racine `/` redirige vers cette route.
- L’écran Gérer l’équipe propose **Supprimer l’équipe** avec recopie du nom exact. La suppression est définitive et partagée : participants (y compris identités archivées), présences, humeurs, baromètres propres à l’équipe, bilans, passages, retours et questions personnalisées sont supprimés dans une transaction. Les autres équipes, espaces techniques et le catalogue global sont conservés. Les anciennes références de sélection sont libérées. Les dépendances restrictives sont supprimées avant la ligne équipe, puis les clés étrangères terminent la cascade ; toute erreur annule l’ensemble. Aucun changement de schéma n’est nécessaire. Après suppression de la dernière équipe, la liste reste vide, même après rechargement, jusqu’à une création explicite. Les sauvegardes en attente bloquent la suppression ; une réponse non confirmée bloque les modifications jusqu’à une nouvelle lecture Neon.
- **`/manage-team`** : ajouter, rechercher, renommer et retirer les membres, individuellement ou par sélection avec confirmation. Une nouvelle équipe ouvre cet écran.
- **`/participants`** : confirmer uniquement les présences et absences du jour, puis continuer vers les humeurs. Le lien « Gérer l’équipe » ouvre la gestion des membres.
- **`/mood`** : consulter les baromètres locaux (fonds et GIF), choisir une humeur **1–4** pour chaque personne présente. Les GIF jouent automatiquement en boucle au chargement et à chaque changement de diapositive ou de baromètre, y compris si la réduction des mouvements est activée (lecture explicitement demandée). **Stop / Reprendre** fige ou reprend les animations de la diapositive actuelle ; **Précédente / Suivante** changent manuellement de diapositive. Aucun changement automatique de diapositive. Les autres animations de l’interface respectent la réduction des mouvements. Au moins une personne présente et toutes ses humeurs sont nécessaires pour continuer.
- **`/timer`** : ordre mélangé contenant uniquement les présents, minuteur par personne, pause, réinitialisation, ajout de 30 secondes, préalerte et fin sonore facultative. Le passage suivant reste manuel.
- **`/statistics`** : les 5 derniers jours civils UTC, aujourd’hui inclus, graphique léger, passages, temps moyen, respect du temps et détails des tours terminés. Pas de bibliothèque graphique lourde. Les baromètres utilisés portent « Déjà utilisé », restent sélectionnables, mais sont exclus du choix automatique ; le baromètre original est un choix manuel.
- **`/help`** : guide illustré en français (lien « Guide » dans le bandeau), accessible même pendant une panne Neon ou après le point du jour. Les quatre illustrations originales sont conservées dans `docs/guide` et publiées par `npm run assets`, jamais modifiées directement dans `public`.

Le bouton **Détail du score** de chaque participant ouvre son temps actif, le pourcentage du budget et le calcul des points. Le bilan transitoire peut détailler les relances connues. Les bilans enregistrés et les points récents affichent le score conservé, le calcul selon le barème actuel et leur écart : les archives ne stockent ni le nombre de relances ni la version du barème, donc aucune cause n’est inventée pour cet écart et aucun ancien total n’est réécrit.

Le **Bilan du jour** présente un tableau de bord compact sans défilement : bandeau de quatre indicateurs, classement paginé selon la hauteur disponible et deux colonnes sur grand écran. Sur mobile et tablette étroite, les boutons « Points & détails » et « Mood meters » alternent les sections sans les empiler. Les choix d’humeur sont filtrables par repère dans l’ordre 1–4 / 2–3 et paginés ; un sélecteur permet de consulter plusieurs baromètres. Sur les écrans courts, « Voir image » ouvre la diapositive dans une fenêtre. Les graphiques ne recalculent pas les scores archivés ; les durées excluent les pauses. La réinitialisation conserve sa confirmation et sa portée partagée pour toute l’équipe.

Le bilan développé sépare deux colonnes : **points et explications** à gauche (indicateurs, classement, zones temporelles) et **baromètres et choix** à droite. Les choix sont groupés par diapositive exacte puis par repère 1–4, avec noms et couleurs distinctes non évaluatives. L’aperçu utilise uniquement la diapositive d’un choix individuel encore inchangé, daté avant la fin du tour et cohérent avec le titre et l’humeur archivés. Sans cette preuve, le titre et les groupes restent visibles avec un message d’image indisponible ; aucun rapprochement approximatif par titre n’est tenté. Les GIF restent en pause jusqu’à une action explicite et désactivés en réduction des mouvements. Entrées et barres de score ont des animations discrètes, sans mouvement sous réduction des animations.

**Démarrer** ouvre le mode de parole : bandeau précédent / personne active centrée / personne suivante, minuteur agrandi et réglages verrouillés (y compris en pause). **Modifier** suspend le décompte et ouvre une fenêtre de réglages ; fermer cette fenêtre garde le minuteur en pause, sans quitter le mode de parole. **Suivant** termine le passage actuel et démarre immédiatement le minuteur de la prochaine personne ; à zéro, le passage reste manuel, sans changement automatique. Le dernier passage termine le tour et arrête le minuteur. Le rechargement revient au mode de préparation.

Après le dernier passage, un classement et le bilan du tour apparaissent. Le score de gestion du temps est visible en direct dans l’anneau : **orange avant 25 %** du budget initial (progression linéaire de 0 à 1 000), **vert entre 25 % et 100 % inclus** (1 000 points, sans inciter à remplir tout le temps), **rouge au-delà de 100 %** (perte linéaire de 100 points par 10 % de dépassement, jusqu’à 0 à 200 %). Les couleurs sont accompagnées d’un libellé. À zéro, le chronomètre continue en dépassement positif et le score décroît jusqu’à Pause ou Suivant, sans changer automatiquement de personne ; l’alerte sonore et la notification ne se déclenchent qu’une fois. Le score final utilise exactement le même calcul que l’aperçu. Une relance après réinitialisation retire 100 points (maximum 200) ; pause/reprise, y compris en dépassement, ne pénalise pas et exclut le temps de pause. Le budget initial et le temps actif cumulé sont conservés lors des réglages et relances. Un passage terminé de moins d’une seconde reste non mesuré. Ce jeu n’évalue ni la qualité de la contribution, ni la productivité, ni les humeurs ; les égalités partagent le rang. Le bilan présente le temps actif, la moyenne, les passages dans le temps et les dépassements, ainsi que la répartition des repères d’humeur. Chaque choix d’humeur conserve son baromètre et sa diapositive : les images et les personnes associées figurent dans le bilan, avec lecture GIF facultative. Les mêmes nombres sur différents baromètres n’ont pas forcément le même sens. Le bilan détaillé courant reste en mémoire ; à la fin du tour, une copie compacte des noms, catégories, titres des baromètres, durées et scores rejoint l’historique des 5 derniers jours, sans images ni progression active. Les scores déjà archivés conservent leur ancien barème ; seuls les nouveaux tours utilisent le nouveau calcul.

Chaque page indique son étape et l’action suivante. Les présences et les états prêts/terminés sont verts ; les absences et le temps écoulé sont rouges ; les informations incomplètes et les avertissements sont orange. Le minuteur passe à l’orange au seuil configuré, puis au rouge dans les dernières secondes (10 secondes maximum, ou la moitié du seuil). Les halos pulsent doucement uniquement pendant le décompte, jamais en pause ni avec la réduction des mouvements. Désactiver la préalerte désactive ces étapes avant zéro. À zéro, une notification urgente et un message persistant demandent de conclure et de passer la parole ; aucun passage automatique n’a lieu.

Ce sont de vraies routes Next.js, pas des vues à fragments d’URL. Les gardes attendent une lecture Neon réussie puis empêchent de sauter les prérequis ; si Neon est inaccessible, le démarrage reste bloqué avec une erreur explicite et une possibilité de réessayer. Modifier une présence ou une humeur invalide la session. Quitter la route du minuteur arrête son exécution. Le compte à rebours, la progression, l’ordre de passage de la session et la diapositive courante sont transitoires en mémoire React : un rechargement exige de recréer l’ordre de passage avant de reprendre le minuteur. Le mélange garde la personne active après le démarrage, y compris en pause. Raccourcis : **Espace** démarrer/pause, **N** suivant, **R** réinitialiser, sans intercepter les contrôles natifs ou les dialogues.

Préserver les contrôles accessibles, le focus visible, les notifications en français, les listes paginées, les panneaux adaptés aux petits écrans et la réduction des mouvements (animations et GIF).

## Architecture

### Chargement et consommation de ressources

Les chargements de route, de l’équipe, des statistiques, des questions et du baromètre affichent des **squelettes statiques** adaptés à la page : pas de shimmer, animation infinie ou temporisation artificielle. Les erreurs Neon gardent leurs messages et boutons de nouvelle tentative ; un squelette ne remplace jamais une panne ni les gardes de validation.

Les lectures indépendantes équipe/historique et catalogue/baromètre quotidien démarrent en parallèle. Le minuteur n’installe aucun intervalle en préparation ou en pause ; pendant la parole, quatre rafraîchissements par seconde remplacent les dix précédents. Les échéances restent la source du temps, et chaque action mesure exactement le temps écoulé avant de modifier le décompte. L’observation des animations est limitée aux attributs utiles et aux listes, sans observer les mutations de texte du compte à rebours.

Les métadonnées publiques des baromètres ont un cache **en mémoire seulement**, 60 secondes pour le catalogue et cinq minutes pour au plus 20 présentations. Les échecs et requêtes annulées ne sont pas mémorisés ; les données d’équipe, les votes et l’historique ne sont pas mis en cache par ce mécanisme. Les images utilisent le décodage asynchrone. Le spectateur ne fait pas de requêtes ni de rafraîchissements de temps lorsque son onglet est caché et resynchronise immédiatement au retour ; la diffusion du facilitateur conserve son renouvellement pour ne pas interrompre un direct en cours.

Le test [loading_performance_smoke](tests/loading_performance_smoke.py) retarde volontairement les réponses pour vérifier les squelettes, les erreurs/reprises, les lectures parallèles et le nombre réel de mises à jour du minuteur. Ces mesures locales ne constituent pas une promesse de latence en production : Neon, le proxy, Google, Redis et le réseau des utilisateurs restent des dépendances externes.

### Direct, présentation, questions et retours

- Sur le minuteur, **Diffusion** ouvre les commandes : **Diffuser en direct**, **Lien spectateur** et **Présentation**. La diffusion est volontaire ; le lien `/spectator?team=…` ouvre une vue sans commandes de réunion ni navigation d’édition. Elle affiche la personne active, la suivante, le temps et les passages terminés, jamais les humeurs. Ce n’est pas une autorisation d’accès : le déploiement reste partagé sans authentification.
- Le facilitateur reste seul maître de son minuteur. Une possession temporaire empêche deux diffuseurs de remplacer simultanément le direct de la même équipe. Les vues interrogent le direct toutes les deux secondes et calculent le décompte depuis une échéance alignée sur le serveur ; pause et dépassement sont conservés. Une perte de connexion masque le compte à rebours plutôt que de prétendre rester synchronisé.
- **Présentation** agrandit le minuteur dans un écran épuré et demande le plein écran du navigateur. **Quitter** ou Échap revient à la mise en page normale, sans réinitialiser le temps. Si le navigateur refuse le plein écran, la présentation reste disponible dans la fenêtre. La vue spectateur propose également ce mode.
- **Questions → Modifier** permet d’enregistrer 1 à 5 questions par équipe, de 160 caractères chacune, ou de rétablir les trois questions initiales. Les changements concurrents sont refusés avec une invitation à recharger ; ces réglages sont enregistrés dans Neon.
- Après le tour, **Utilité du point · facultatif** ouvre trois réponses : Utile, Mitigé, Pas utile. Aucune réponse n’est obligatoire et aucun commentaire libre n’est demandé. Le participant du bilan doit être choisi explicitement ; sans authentification, son identité n’est pas vérifiée et les réponses ne sont pas anonymes. Une nouvelle réponse remplace la précédente pour ce participant et ce bilan. Les retours sont supprimés avec le bilan et suivent sa rétention de cinq jours.

**Déploiement du direct :** sans configuration supplémentaire, le canal temporaire utilise la mémoire du processus Next.js, adaptée à un serveur local/une instance unique. Pour Vercel ou plusieurs instances, configurer côté serveur `UPSTASH_REDIS_REST_URL` (HTTPS) et `UPSTASH_REDIS_REST_TOKEN`. Ne jamais exposer le jeton via une variable `NEXT_PUBLIC_*`. Les écritures Redis sont atomiques, avec un TTL de 15 secondes renouvelé pendant la diffusion ; quitter la page ou arrêter le direct libère le canal. Redis ne sert ni d’archive ni de reprise de session : le facilitateur ne restaure jamais un compte à rebours depuis ce canal. Choisir un service Redis sans sauvegarde durable pour conserver cette garantie de données éphémères. L’interface signale explicitement la portée « serveur local uniquement » sans Redis partagé.

Appliquer la migration [0004](drizzle/0004_slim_emma_frost.sql) avant d’utiliser les questions personnalisées et les retours. Les trois nouvelles tables sont relationnelles : réglages/révision par équipe, questions ordonnées et retours liés aux passages archivés avec suppressions en cascade. Les tests [meeting-store](tests/meeting-store.test.ts) vérifient la migration dans PGlite, l’isolation, les conflits, les remplacements et la rétention ; [meeting_features_smoke](tests/meeting_features_smoke.py) couvre les interfaces sur mobile et ordinateur avec APIs simulées, sans écritures Neon réelles.

### Interface Material UI

Les contrôles, surfaces, notifications et dialogues utilisent Material UI avec un thème commun bleu/orange dans [src/providers/design-provider.tsx](src/providers/design-provider.tsx). L’intégration App Router collecte les styles côté serveur ; les couches CSS donnent la priorité aux utilitaires Tailwind pour la géométrie responsive. Tailwind reste dédié à la composition compacte des pages. La navigation est une chronologie connectée à trois étapes, avec liens réels, étapes verrouillées, repères actifs et étapes terminées. Les changements de route et d’étape, dialogues et réorganisations sont animés ; la préférence de réduction des mouvements est respectée. Les animations de navigation ne remontent pas les gardes de parcours et ne conservent jamais une ancienne page interactive. Les contrôles principaux conservent des cibles tactiles d’au moins 44 px, y compris sur téléphone.

| Emplacement | Responsabilité |
| --- | --- |
| [src/app](src/app) | Routes, layout racine, métadonnées et états d’erreur ; les dossiers `_components` sont privés à leur route. |
| [src/components](src/components) | Composants partagés : cadre de l’application, dialogues, pagination, titres et onglets. |
| [src/hooks](src/hooks) | Comportements React : gardes de parcours, cycle de vie et actions du minuteur. |
| [src/providers](src/providers) | État React partagé, chargement et sauvegarde via les API Neon, notifications. |
| [src/lib](src/lib) | Helpers purs de validation, mélange, calcul du temps et normalisation du catalogue ; adaptateurs explicites de persistance Neon et d’audio. |
| [src/types](src/types) | Contrats TypeScript du domaine. |
| [src/components/ui/styles.ts](src/components/ui/styles.ts) | Recettes Tailwind partagées : boutons, cartes, champs, badges et structure des routes. |
| [src/app/globals.css](src/app/globals.css) | Entrée Tailwind v4, tokens de marque, règles de base minimales et keyframes ; aucune feuille de styles de composants. |
| [postcss.config.mjs](postcss.config.mjs) | Intégration du plugin PostCSS Tailwind au build Next.js. |

Les APIs navigateur restent côté client et dans des effets/gestionnaires appropriés. Le compte à rebours utilise une échéance, pas un cumul de ticks. Les noms sont rendus comme texte React, jamais comme HTML. Palette Infomil : bleu **#205f9d**, orange **#ec8b23**, blanc ; le logo local est une recréation vectorielle.

Les mises en page, variantes d’état et points de rupture sont exprimés directement en utilitaires Tailwind dans les composants. Les anciennes feuilles de styles ont été supprimées, ainsi que les blocs UI morts et la dépendance directe Zod (qui reste une dépendance transitive des outils ESLint). Les styles calculés à l’exécution restent nécessaires pour les GIF superposés, l’anneau du minuteur et la progression. Les fichiers d’export, tests, sources d’images et HTML de secours sont utilisés et conservés.

## Ressources et déploiement

### Mode Google SVG à la demande (par défaut)

Le lecteur utilise désormais une liste de **888 URLs de présentations**, dans [src/lib/remote-mood-catalog.json](src/lib/remote-mood-catalog.json), indépendante de l’ancien corpus local. Il ne télécharge plus les PowerPoint et ne publie plus les images locales au démarrage/build. Seuls le logo, le secours HTML et un indicateur de mode sont publiés. Les sources existantes ne sont pas supprimées.

Un indicateur de chargement apparaît pendant la lecture du catalogue, des diapositives et de leur image. Les présentations utilisées sont étiquetées et exclues du choix automatique ; elles restent disponibles en choix manuel, comme le baromètre original. Si une présentation ne peut pas être chargée, une invitation à choisir ou réessayer remplace son contenu ; si son image échoue après sélection, un secours visuel original peut apparaître. Repères du baromètre original : **1 = mauvaise humeur / énergie élevée ; 2 = mauvaise humeur / énergie basse ; 3 = bonne humeur / énergie basse ; 4 = bonne humeur / énergie élevée**. Ces repères ne décrivent pas nécessairement les présentations externes.

À la sélection d’un baromètre, les routes Next.js lisent les identifiants de diapositives du lecteur public Google, puis demandent chaque image via l’export SVG de Google. Le navigateur affiche le SVG dans une image, jamais en HTML injecté. Les résultats réutilisent ces mêmes URLs. Un cache mémoire borné à 32 Mo conserve les réponses au maximum cinq minutes lors des accès ; aucun SVG ou PPTX n’est enregistré sur disque. Un hébergeur peut appliquer son propre cache HTTP.

**Aucun PowerPoint, autre ordinateur Windows, service de conversion ou clé API Google n’est nécessaire.** Sur Windows, [scripts/fetch-google-slide.ps1](scripts/fetch-google-slide.ps1) utilise le proxy système et ses identifiants Windows si nécessaire. Sur Linux et les plateformes comme Vercel, les routes utilisent directement HTTPS. L’accès Internet à Google est indispensable ; les présentations privées/refusées ne sont pas contournées. Les routes limitent les requêtes au catalogue, jamais à une URL libre. Le SVG est servi avec une politique sandbox et sans scripts.

**Limite : les SVG exportés sont statiques. Les GIF et animations PowerPoint ne sont pas préservés.** Les images matricielles intégrées restent matricielles même dans un SVG ; le format ne garantit pas un fichier plus petit. La première ouverture dépend du temps de réponse Google. Son export public n’est pas une API contractuelle : quotas, permissions ou changements du lecteur peuvent interrompre le service.

Commandes : `npm run mood:catalog` régénère la liste depuis le rapport existant sans télécharger les présentations ; l’option `-- -Refresh` relit les liens publics de Google Sites sans télécharger les PowerPoint. Après une modification, reconstruire/redéployer. Pour retrouver le mode local animé, définir `MOOD_LOCAL_ASSETS=1` dans l’environnement ou dans le fichier de configuration local ignoré par Git, puis relancer `npm run dev` ou reconstruire. Ce mode republie les ressources locales volumineuses. Ne définir aucune ancienne variable `MOOD_SERVICE_*` : le service séparé a été retiré.

### Ancien mode local (optionnel)

[scripts/prepare-assets.mjs](scripts/prepare-assets.mjs) s’exécute via **predev** et **prebuild**, ou explicitement avec `npm run assets`. Il génère [public](public) : logo, HTML de secours, catalogue JSON issu du [catalogue exporté](mood-meters/catalog.js) et images de [mood-meters/slides](mood-meters/slides). Les images et fichiers fixes sont publiés par **liens physiques** lorsque possible, sinon par copie. Ne modifiez pas les sorties générées ; les liens physiques peuvent partager le contenu avec leur source.

Conserver les sources racine [infomil-logo.svg](infomil-logo.svg) et [mood-meter.html](mood-meter.html), requises par la publication. **Ne jamais publier les PowerPoint sources**, rapports ou métadonnées internes dans le répertoire public. Les [scripts](scripts) de téléchargement/export et [mood-meters](mood-meters) restent indépendants de React.

Le corpus comprend **888 présentations, environ 9,6 Go** : vérifier le budget de stockage, le nombre de fichiers, les limites d’upload/build et la bande passante de l’hébergeur avant de déployer. Les liens physiques économisent de l’espace local, pas le budget des ressources déployées. Ne supposez pas qu’un hébergement gratuit peut accueillir l’ensemble.

L’[exporteur PowerPoint existant](scripts/export-mood-meters.ps1) est inchangé : rendu Windows/PowerPoint, fonds PNG et GIF superposés avec leur géométrie. Un export reconstruit les sorties générées ; les sources restent intactes. Après tout nouvel export, **relancer `npm run assets`, reconstruire et redéployer**. Le lecteur React utilise le catalogue publié, et le [baromètre HTML](mood-meter.html) sert de secours. Utiliser uniquement les ressources dont les droits autorisent l’utilisation et la redistribution.

## Persistance et migration

**Neon est l’unique persistance faisant autorité** pour les participants (noms, présences et humeurs), les réglages, les baromètres utilisés et l’historique des tours terminés. L’application ne lit ni n’écrit cookies, `localStorage`, `sessionStorage` ou IndexedDB : aucun identifiant privé de navigateur, cache métier persistant, archive locale ou mode de secours hors ligne. Le contexte d’équipe est conservé dans le paramètre d’URL `team` : un rechargement restaure cette équipe après vérification dans la liste Neon. Un lien sans contexte ou un identifiant supprimé utilise l’équipe proposée par la base. Chacun peut choisir une équipe sans changer la sélection des autres visiteurs ; le lien peut aussi être partagé ou mis en favori. Chaque requête d’équipe exige son identifiant explicite, vérifié dans Neon.

Le minuteur en cours, sa progression, l’ordre de passage de la session et la diapositive courante restent en mémoire React, sans restauration après rechargement : il faut recréer l’ordre de passage. Une diffusion activée publie uniquement un miroir temporaire du temps et des noms dans le canal éphémère décrit plus haut ; celui-ci n’est jamais relu pour reprendre le minuteur. À la fin d’un tour, le bilan compact est sauvegardé dans Neon, avec une rétention de 5 jours civils UTC, aujourd’hui inclus. Celui du jour peut être consulté sur tous les appareils.

**Aucun import automatique des anciennes données navigateur n’est effectué**, même sur la même origine. Les anciennes clés ne sont ni lues ni effacées automatiquement. Les données de l’ancien site, y compris sous `file://`, ne sont donc pas reprises dans Neon ; une éventuelle migration explicite est une opération distincte, non incluse dans le démarrage.

### Équipes et baromètre quotidien

Si le CLI standard ne peut pas ouvrir sa connexion WebSocket sur le réseau Windows, l’opérateur peut exécuter explicitement `npx tsx scripts/migrate-http.ts` : ce script utilise le migrateur HTTP officiel de Drizzle, les mêmes fichiers et le même journal, avec le proxy système existant. `npm run db:migrate` reste le CLI standard. Cette solution n’est jamais déclenchée par une requête utilisateur ; vérifier ensuite avec `npm run db:verify`.

**Chargement automatique du catalogue :** si Neon ne contient aucun baromètre distant, ou si la période de sept jours est expirée, le serveur relit la page publique SCRED, extrait toutes les présentations et leurs catégories, puis les enregistre atomiquement avant de répondre au menu déroulant. Les chargements suivants lisent Neon sans refaire cet appel source. Les nouvelles présentations sont sélectionnables sans reconstruction ; les identifiants déjà publiés sont conservés. Les liens historiques absents de la page restent disponibles sous « Autres ». Si la source échoue ou renvoie une page incomplète, aucune liste partielle n’est enregistrée et l’ancien cache n’est pas effacé. La migration 0003 doit déjà être appliquée : une table manquante n’est pas une table vide et n’est jamais créée lors d’une requête utilisateur.

Le catalogue distant (identifiants Google, titres et catégories) et les listes de diapositives résolues sont partagés dans Neon via trois tables de cache dédiées : `remote_mood_cache_state`, `remote_mood_catalog` et `remote_mood_pages`. Appliquer la migration 0003 avec `npm run db:migrate` avant de déployer cette version. Au premier accès, le catalogue publié initialise le cache ; chaque présentation est ensuite chargée à la demande, une seule fois par période. **Sept jours après l’initialisation, la première requête suivante supprime tout le catalogue et toutes ses listes de diapositives du cache, puis réinitialise le catalogue atomiquement.** Il s’agit d’une expiration à la demande, sans tâche planifiée : aucune suppression ne s’exécute pendant que le site est inutilisé. Les autres visiteurs et instances réutilisent les URL enregistrées en base. Les équipes, participants, votes, choix quotidiens et historiques ne sont jamais supprimés par cette purge. Les SVG eux-mêmes restent récupérés à la demande avec un cache mémoire borné de cinq minutes, sans stockage des images ou des PowerPoints en base. Une panne de Google ne laisse pas de liste partielle en base ; une panne de Neon est signalée, sans cache navigateur de remplacement.

Le catalogue reprend les **12 catégories du site SCRED**, affichées en français dans des groupes du menu déroulant avec leur nombre de baromètres. Les titres et identifiants restent inchangés ; les entrées absentes de la page source apparaissent sous « Autres ». Les catégories sont chargées depuis les titres de sections publics, pas déduites des noms. Pour actualiser uniquement ces métadonnées sans télécharger de présentations ni modifier le corpus PowerPoint : `npm run mood:catalog -- -CategoriesOnly`, puis reconstruire et redéployer. Une panne de la source pendant cette actualisation laisse le catalogue existant intact ; la navigation courante utilise le catalogue publié, sans appel supplémentaire à SCRED.

Le sélecteur dans la barre de navigation permet de **rechercher, créer et choisir une équipe**, sans limite applicative sur le nombre d’équipes. Toutes les équipes et leurs participants sont accessibles à tous les visiteurs du même site, y compris sur un nouveau téléphone. Chaque équipe conserve ses propres membres, présences, humeurs, réglages et statistiques. Le choix d’équipe reste indépendant par navigateur. Après création/sélection, le parcours revient à Participants. Une sauvegarde en attente bloque le changement d’équipe. Les requêtes portent explicitement l’identifiant de l’équipe partagée.

Chaque équipe utilise **un baromètre partagé par jour civil à Maurice** (`Indian/Mauritius`, UTC+4). **Avant le premier vote**, chaque ouverture ou rechargement des Humeurs choisit aléatoirement un autre baromètre non utilisé, confirmé dans Neon avant de voter. Le catalogue et le bouton aléatoire restent disponibles pour un choix manuel. Si aucun autre baromètre non utilisé ne reste, le choix partagé existant est conservé ; à la première initialisation sans candidat, l’original est utilisé. Le premier vote ou un bilan terminé verrouille le baromètre, y compris après rechargement, pour éviter de mélanger des repères différents. Le serveur impose cette règle sous verrou d’équipe, y compris entre appareils ; un vote concurrent conserve le choix verrouillé. Les check-ins précédents doivent être renseignés à nouveau le jour suivant. Les decks indisponibles peuvent être réessayés ou remplacés avant le premier vote.

La migration [0002](drizzle/0002_workspace_daily_meters.sql) ajoute `workspaces`, les noms/appartenances historiques des équipes et `team_daily_meters`, avec une clé unique équipe–date. Les anciennes données et références sont conservées ; les anciennes sélections privées ne sont plus lues ni modifiées. Un seul espace commun en base sert aux nouvelles équipes, sans créer d’espace par visiteur. Les douze tables restent relationnelles sans colonne JSON ; les limitations physiques de l’hébergement continuent à s’appliquer.

### Neon : configuration privée

La variable serveur `DATABASE_URL` se place dans le fichier d’environnement racine **.env**, ignoré par Git. Ne jamais y committer des identifiants ; si le mot de passe a été partagé dans une conversation, le renouveler dans Neon et remplacer la valeur locale. L’ancienne variable `COOKIE_SECURE` n’est plus utilisée.

Le classement historique sur `/statistics` regroupe les participants par identifiant stable sur les 5 jours civils UTC, aujourd’hui inclus. Le rang dépend du **score moyen / 1 000** des passages mesurés, pas du nombre de participations ; les égalités partagent le rang et les passages non mesurés restent sans score. Noms récents, nombre de passages et durée moyenne sont affichés dans une liste compacte paginée par huit. Le classement du tour courant reste disponible à la fin du minuteur. Les humeurs ne modifient aucun score.

Dans **Neon → Connect**, sélectionner l’endpoint **ep-little-cloud-aojwgz1g**, puis copier sa **chaîne de connexion PostgreSQL complète avec pooler et TLS**. Le nom d’endpoint seul ne contient ni la région, ni le rôle, ni le mot de passe : il ne suffit pas pour se connecter. Ajouter cette chaîne comme variable serveur **`DATABASE_URL`** dans la configuration locale ignorée par Git et dans les variables de l’hébergeur, puis redémarrer/redéployer. Ne jamais la préfixer par `NEXT_PUBLIC_`, la publier ou la transmettre dans le chat.

La persistance utilise **Drizzle ORM avec le pilote Neon HTTP**, avec des tables relationnelles normalisées et **aucune colonne JSON/JSONB persistée**. Le [schéma typé](src/db/schema.ts) définit :

| Table | Responsabilité |
| --- | --- |
| teams | Équipe partagée, espace de création historique, réglages, révision optimiste et jeton transactionnel. |
| participants | Identité et nom courant ; conservés si un historique les référence. |
| team_members | Appartenance à la liste active, position et présence. |
| participant_check_ins | Humeur, date PostgreSQL avec fuseau et références de diapositive. |
| mood_meters / mood_meter_identifiers | Titres historiques et identifiants de catalogue distincts : un titre seul ne prouve pas l’identité d’un deck. |
| mood_meter_slides | Contexte de diapositive unique, lié au baromètre. |
| team_used_mood_meters | Association équipe–baromètre utilisé et ordre. |
| standup_sessions / speaking_turns | Sessions terminées et passages individuels ; le nom au moment du passage reste une valeur historique. |

Clés primaires/composites, clés étrangères, contraintes d’unicité et `CHECK` imposent l’intégrité. Toutes les références sont isolées par équipe privée. Les écritures de profil et de leurs lignes associées sont atomiques via `db.batch`, avec une révision et un jeton de transaction qui empêchent un onglet périmé de modifier les enfants. Les sessions terminées sont idempotentes. Le JSON n’est utilisé que pour le transport HTTP et les paramètres/résultats SQL, jamais comme stockage. Aucun PowerPoint, SVG ou GIF n’est stocké dans Neon. Adaptateurs : [src/lib/database.ts](src/lib/database.ts), [src/lib/relational-store.ts](src/lib/relational-store.ts). Routes : [src/app/api/team/route.ts](src/app/api/team/route.ts) et [src/app/api/history/route.ts](src/app/api/history/route.ts).

**Avant de démarrer ou déployer**, exécuter `npm run db:migrate` avec `DATABASE_URL` configurée. Cette commande lance désormais **`drizzle-kit migrate`**, sans runner personnalisé. Les tables ne sont plus créées lors des requêtes utilisateur. La [configuration Drizzle](drizzle.config.ts) charge les variables avec le chargeur Next.js (les configurations locales prioritaires peuvent remplacer la valeur racine) et conserve explicitement le journal existant `drizzle.__drizzle_migrations` : les migrations déjà appliquées ne sont pas rejouées. Ne pas utiliser de commande destructive de type push/reset sur une base existante. Après modification du schéma : `npm run db:generate`, examiner le SQL généré, `npm run db:check`, puis `npm run db:migrate`. Le rôle de migration doit pouvoir créer tables/index et le journal Drizzle ; en production le rôle applicatif peut être limité aux lectures/écritures. Les erreurs du CLI peuvent inclure des détails de connexion ; ne pas publier ses journaux sans les examiner et les expurger.

La migration initiale adopte les anciennes tables. La [migration relationnelle](drizzle/0001_abandoned_snowbird.sql) verrouille ces tables, convertit leurs profils et **tous** leurs historiques (sans appliquer la rétention pendant la conversion), compare les champs et les nombres de lignes, puis supprime les anciennes tables JSON seulement après vérification. Une valeur non prise en charge annule la transaction complète. Le migrateur PostgreSQL de Drizzle utilise une transaction pour les migrations en attente et leurs entrées de journal ; arrêter les anciens serveurs avant migration et déployer la nouvelle version ensuite. Effectuer également une sauvegarde/branche Neon suivant les procédures de l’hébergeur avant une migration de production. `npm run db:verify` vérifie les douze tables et l’absence de colonnes JSON. Un code `UND_ERR_CONNECT_TIMEOUT` ou `ENOTFOUND` signale un problème réseau, pas une migration réussie ; ne jamais désactiver TLS.

Les actions sont validées côté interface, au fournisseur d’état et à l’API : noms de 1 à 60 caractères après suppression des espaces extérieurs, sans caractères de contrôle ; maximum 100 personnes ; humeurs 1–4, identifiants uniques et réglages bornés. Les noms sont toujours du texte React, jamais du HTML injecté. Le bouton de modification conserve l’identité, la présence et l’humeur. Les suppressions individuelles et groupées demandent confirmation. Les entrées invalides sont rejetées, pas tronquées silencieusement. Les [tests de base](tests/database.test.ts) exécutent la migration et les écritures dans PostgreSQL isolé via PGlite, sans accès à Neon.

**Proxy Windows avec les identifiants actuels** : [src/lib/neon-network.ts](src/lib/neon-network.ts) configure le pilote Neon HTTP pour utiliser [scripts/neon-proxy-request.ps1](scripts/neon-proxy-request.ps1), le proxy système et `ProxyUseDefaultCredentials`. Aucun mot de passe Windows n’est demandé ni stocké. La connexion Neon, ses en-têtes et les requêtes SQL transitent uniquement par stdin vers PowerShell (ni arguments de processus, ni fichiers temporaires, ni journaux). TLS reste vérifié ; redirections refusées, délais et tailles bornés. Sur Linux/Vercel, le pilote conserve HTTPS natif. **Seuls l’application et `npm run db:verify` partagent cet adaptateur HTTP.** `npm run db:migrate` / `npx drizzle-kit migrate` utilise le pilote WebSocket Neon et nécessite un accès DNS/WebSocket autorisé vers Neon ; il ne bénéficie pas automatiquement des identifiants du proxy Windows. Sur ce poste, l’essai du CLI a échoué avec `ENOTFOUND` avant l’application de SQL de migration. Exécuter les migrations depuis un environnement réseau autorisé (par exemple CI), sans désactiver TLS. Les trois migrations précédemment appliquées restent enregistrées ; la vérification HTTP confirme douze tables applicatives sans colonne JSON. Le script PowerShell doit être présent au déploiement Windows de l’application, et le compte qui exécute Node doit disposer de l’accès proxy autorisé.

**Accès partagé, sans compte et sans cookie applicatif** : tous les visiteurs du même déploiement peuvent voir et modifier les équipes, participants, humeurs et bilans, et réinitialiser le point du jour après confirmation. Les équipes des anciens espaces sont également visibles sans copie ni migration. Les anciens cookies éventuellement présents sont ignorés ; ils peuvent être effacés sans perte de données. Il n’y a pas d’authentification : protéger le déploiement par un contrôle d’accès externe si les données doivent rester internes. À chaque lecture ou enregistrement d’historique d’une équipe, les sessions antérieures à minuit UTC quatre jours avant aujourd’hui sont supprimées de Neon, avec leurs passages individuels en cascade. Les équipes, participants et résultats des cinq jours conservés ne sont pas supprimés. Le nettoyage est effectué à la demande, sans tâche planifiée ni nouvelle migration pour ce changement de durée.

**Un seul point quotidien terminé par équipe et par jour à Maurice.** Les fins de tour sont sérialisées sous verrou d’équipe ; une deuxième fin différente est refusée, les retransmissions du même bilan restent idempotentes. Le bilan du jour est chargé avant le parcours. Les Humeurs et le Minuteur proposent **Voir le bilan du jour** ou **Réinitialiser aujourd’hui**. Participants reste accessible avec un lien vers ces choix. Après confirmation, réinitialiser supprime les résultats et humeurs du jour pour tous les appareils, mais conserve les équipes, participants, jours précédents et baromètre du jour. Les anciennes révisions de profil sont invalidées. Aucune nouvelle migration n’est nécessaire.

Le fournisseur attend une **lecture Neon réussie** avant de débloquer le parcours et les gardes de route. Une configuration absente ou une base inaccessible bloque clairement le démarrage ; une base vide ne déclenche aucun import local. Un conflit de version entre appareils ne remplace pas silencieusement les profils. L’API limite et valide les données et refuse les écritures cross-origin. Le partage entre navigateurs utilise la même base Neon ; l’authentification n’est pas incluse.

Après le chargement initial, les requêtes de sauvegarde non envoyées ou en échec restent **uniquement en mémoire** et sont retentées ; cet état provisoire n’est ni une sauvegarde ni un mode hors ligne. Tant que des écritures sont en attente, un avertissement `beforeunload` signale le risque de perte en quittant ou rechargeant la page. Une fermeture ou un rechargement peut perdre ces modifications et les tours non encore enregistrés : seuls les enregistrements confirmés par Neon sont durables. Effacer les données du navigateur ne supprime aucune donnée Neon.

## Validation

### Personnes présentes mais pas encore arrivées

Dans le bilan d’humeur, **Plus tard** reporte explicitement l’humeur et le passage d’une personne sans la marquer absente. Au moins une personne doit avoir voté et être prête pour commencer. Le minuteur ignore les personnes en attente lors de **Suivant** et du mélange ; elles ne sont jamais marquées comme ayant terminé. **↷ Reporter** permet également de reporter un passage, y compris celui en cours : le décompte s’arrête et les secondes déjà utilisées sont conservées.

À leur arrivée, utiliser **En attente** dans le panneau Participants, ou **Modifier** pendant un passage, pour choisir leur humeur et les ajouter en fin de tour. Modifier met le décompte en pause ; rejoindre ne le relance pas et ne remet pas à zéro le passage courant. Le bilan final n’est archivé que lorsque toutes les personnes ont terminé. Les reports et la progression du minuteur restent temporaires et sont effacés au rechargement ; seules les humeurs sont sauvegardées dans Neon.

Les contrôles de code et de build sont `npm run lint`, `npm run typecheck`, `npm run test` et `npm run build` ; la cohérence des migrations se vérifie avec `npm run db:check`. Leur réussite ne prouve pas une connexion à Neon ni l’application effective des migrations.

Les ajouts Neon/historique disposent de [tests/history.test.ts](tests/history.test.ts) et de [tests/persistence_smoke.py](tests/persistence_smoke.py) (`python tests/persistence_smoke.py`, serveur local requis). Ces scénarios utilisent des réponses API mockées, pas une archive locale : **ils ne constituent aucune preuve de connexion à une base Neon réelle**. Le [test quotidien sans stockage](tests/daily_round_smoke.py) interdit cookies JavaScript, localStorage, sessionStorage et IndexedDB, vérifie deux contextes indépendants sur téléphone et ordinateur et confirme qu’aucun cookie n’est créé. Le [test des contextes d’équipe](tests/team_context_smoke.py) vérifie la restauration par URL, l’isolation des équipes, le choix aléatoire au chargement et les votes concurrents. Une vérification Neon réelle exige la configuration et les migrations, puis des lectures et écritures sans mocks. Après rechargement, le paramètre d’URL `team` restaure l’équipe ; recréer l’ordre de passage si le tour n’était pas terminé.

Le [scénario navigateur historique](tests/browser_smoke.py) utilise Python Playwright avec Chromium et un serveur sur http://localhost:3000. **Il est obsolète pour le contrat actuel** : ses assertions de stockage local, de fonctionnement sans stockage et de GIF/pause concernent l’ancien mode local animé, pas la persistance Neon exclusive ni les SVG Google statiques. Il doit être adapté avant de servir de validation du parcours actuel ; sa réussite éventuelle ne prouve pas le fonctionnement de Neon. Les vérifications historiques de pagination avec 40 personnes couvraient les trois routes en 320×568, 390×844, 768×1024, 1024×576, 1366×768 et 1920×1080, sans débordement ; elles ne remplacent pas une nouvelle exécution. Les dépendances Python de ces vérifications optionnelles ne sont pas installées par npm.

Ces vérifications locales ne valident pas les quotas ou le déploiement de l’hébergeur. Après une modification, relancer les contrôles concernés.
